# Keyword Analysis API Decisions

## Decision 007: 키워드 분석 결과는 자기소개서별 최신 결과만 유지한다

### 결정

키워드 분석 결과는 첨삭 버전별로 모두 보존하지 않고, 자기소개서별 최신 결과만 유지한다.

키워드 분석 결과가 없는 상태에서 사용자가 `키워드 분석하기`를 실행하면 새 결과를 생성한다. 분석 기준이 된 첨삭 버전은 `sourceReviewVersionId`로 기록한다.

키워드 분석 결과가 있는 상태에서 사용자가 `AI 키워드 재분석`을 실행하면 기존 결과 리소스를 재사용해 가장 최근 첨삭 버전 기준으로 다시 분석하고, 성공 시 기존 결과를 최신 분석 결과로 덮어쓴다.

API 형태:

```http
POST /cover-letters/{coverLetterId}/keyword-analysis
GET  /cover-letters/{coverLetterId}/keyword-analysis/latest
```

### PRD 근거

- 키워드 분석 첫 화면에는 `키워드 분석하기` 버튼이 있다.
- 키워드 분석 결과 화면에는 `AI 키워드 재분석` 버튼이 있다.
- 키워드 분석 결과는 워드 클라우드와 주요 키워드 중요도 지표로 보여준다.
- PRD에는 키워드 분석 히스토리나 버전별 키워드 비교 화면이 없다.

### 고려한 대안

1. 첨삭 버전별 키워드 분석 결과 보존
   - `sourceReviewVersionId` 기준으로 `v0.1`, `v0.2`의 분석 결과를 각각 저장한다.
   - 재첨삭 전후 키워드 변화를 추적할 수 있다.
   - 하지만 화면에서 어떤 분석 결과를 보여줄지 추가 기준이 필요하고 데이터가 더 쌓인다.

2. 자기소개서별 최신 키워드 분석 결과만 유지
   - 자기소개서당 현재 유효한 키워드 분석 결과를 하나만 유지한다.
   - API와 화면이 단순하고, PRD의 단일 워드클라우드 화면과 잘 맞는다.
   - `AI 키워드 재분석`은 같은 리소스를 최신 결과로 갱신한다.

### 선택 이유

PRD는 키워드 분석을 히스토리 기능이 아니라 현재 자기소개서에 대한 단일 분석 화면으로 설명한다. 따라서 자기소개서별 최신 결과만 유지하는 방식이 현재 요구사항에 더 적합하다.

### 트레이드오프

- 장점
  - API와 화면 상태가 단순하다.
  - 사용자는 현재 유효한 키워드 분석 결과만 보면 된다.
  - 불필요한 분석 히스토리 저장을 피할 수 있다.

- 단점
  - 과거 첨삭 버전에 대한 키워드 분석 결과는 보존되지 않는다.
  - `AI 키워드 재분석`을 실행하면 기존 분석 결과가 덮어써진다.
  - 재첨삭 전후 키워드 변화 비교 기능을 만들려면 보존 정책을 다시 확장해야 한다.



## Decision 021: 키워드 분석 결과는 상위 20개를 제공한다

### 결정

키워드 분석 결과는 중요도 기준 상위 20개 키워드를 제공한다.

각 키워드는 1~100 범위의 중요도를 가진다.

예상 구조:

```json
{
  "keywords": [
    {
      "keyword": "백엔드",
      "importance": 95
    }
  ]
}
```

### PRD 근거

- 키워드 분석 결과는 워드 클라우드 형태로 나타난다.
- 지표에서는 주요 키워드 각각에 대해 중요도를 1~100 숫자로 나타낸다.

### 고려한 대안

1. 상위 10개
   - 워드클라우드와 지표가 깔끔하다.
   - 하지만 자기소개서가 긴 경우 일부 키워드가 빠질 수 있다.

2. 상위 20개
   - 워드클라우드가 더 풍부해진다.
   - 다만 지표 목록이 길어지고 중요도가 낮은 키워드가 섞일 수 있다.

3. 최대 20개, 중요도 50 이상만
   - 품질 필터링이 가능하다.
   - 결과 개수가 매번 달라져 UI 레이아웃이 불안정할 수 있다.

### 선택 이유

키워드 분석 화면은 워드클라우드를 중심으로 보여준다. 워드클라우드는 10개보다 20개가 더 풍부하게 보일 수 있으므로, 상위 20개를 제공하는 것이 현재 화면 요구에 더 적합하다.

### 트레이드오프

- 장점
  - 워드클라우드가 더 풍부해진다.
  - 자기소개서의 다양한 키워드를 보여줄 수 있다.
  - 결과 개수가 고정되어 프론트엔드 레이아웃을 예측하기 쉽다.

- 단점
  - 지표 목록이 길어질 수 있다.
  - 중요도가 낮은 키워드도 포함될 수 있다.
  - 모바일 화면에서는 표시 밀도 조정이 필요할 수 있다.



## Decision 028: 재첨삭 완료 시 기존 키워드 분석 결과를 유지한다

### 결정

자기소개서 재첨삭이 완료되어 새 `ReviewVersion`이 생성되어도 기존 키워드 분석 결과는 삭제하지 않는다.

사용자가 `AI 키워드 재분석`을 실행하면 같은 `KeywordAnalysis` 리소스를 `PROCESSING`으로 전환하고, 가장 최근 첨삭 버전을 기준으로 다시 분석한다. 성공 시 기존 결과를 최신 분석 결과로 덮어쓴다.

### PRD 근거

- 키워드 분석은 LLM에 의해 첨삭된 자기소개서를 바탕으로 핵심 키워드를 보여준다.
- 키워드 분석 화면은 단일 워드클라우드와 지표를 보여준다.
- PRD에는 키워드 분석 히스토리나 버전별 비교 기능이 없다.

### 고려한 대안

1. 기존 키워드 분석 결과 유지 후 사용자 재분석 시 갱신
   - 분석 결과는 생성 당시 `sourceReviewVersionId` 기준으로 유지된다.
   - 사용자가 `AI 키워드 재분석`을 실행할 때만 최신 첨삭 버전 기준으로 결과를 갱신한다.
   - 사용자가 요청하지 않은 LLM 비용이 발생하지 않고, 기존 결과도 갑자기 사라지지 않는다.

2. 재첨삭 완료 시 키워드 분석 결과 삭제
   - 최신 첨삭 기준이 아닌 분석 결과를 화면에서 제거한다.
   - 사용자는 필요할 때 다시 분석을 실행한다.

3. 재첨삭 완료 시 키워드 분석 자동 재실행
   - 항상 최신 분석 결과를 유지할 수 있다.
   - 하지만 사용자가 요청하지 않아도 LLM 비용이 발생한다.

### 선택 이유

키워드 분석은 사용자가 명시적으로 실행하는 LLM 작업이다. 재첨삭 완료만으로 기존 분석 결과를 삭제하면 사용자가 요청하지 않았는데 화면 상태가 사라진다. 따라서 기존 결과는 유지하고, 사용자가 `AI 키워드 재분석`을 실행할 때만 최신 첨삭 버전 기준으로 갱신한다.

### 트레이드오프

- 장점
  - 사용자가 요청하지 않은 상태 변경이 발생하지 않는다.
  - 기존 키워드 분석 결과가 갑자기 사라지지 않는다.
  - 자동 LLM 비용이 발생하지 않는다.

- 단점
  - 재첨삭 후 기존 분석 결과가 최신 첨삭 버전 기준이 아닐 수 있다.
  - 화면에서 `sourceReviewVersionId` 또는 재분석 유도를 명확히 표현해야 할 수 있다.



## Decision 029: 키워드 분석 결과 화면에서 재분석을 제공한다

### 결정

키워드 분석 결과가 이미 있으면 키워드 분석 결과 화면에 `AI 키워드 재분석` 버튼을 노출한다.

사용자가 `AI 키워드 재분석`을 실행하면 새 `KeywordAnalysis` 리소스를 만들지 않고 기존 `KeywordAnalysis`를 `PROCESSING`으로 전환한 뒤, 가장 최근 첨삭 버전인 `CoverLetter.latestReviewedVersionId`를 기준으로 다시 분석한다. 분석 성공 시 기존 `keywords`, `sourceReviewVersionId`, `completedAt`을 최신 결과로 갱신한다.

API도 같은 정책을 따른다. 현재 유효한 키워드 분석 결과가 있는 자기소개서에 `POST /cover-letters/{coverLetterId}/keyword-analysis`를 호출하면 같은 `keywordAnalysisId`를 재사용해 새 LLM Job을 시작한다.

API 형태:

```http
POST /cover-letters/{coverLetterId}/keyword-analysis
```

### PRD 근거

- 키워드 분석 첫 화면 중앙에는 `키워드 분석하기` 버튼이 있다.
- 키워드 분석 결과 화면에는 `AI 키워드 재분석` 버튼이 있다.
- 키워드 분석 결과는 워드 클라우드와 주요 키워드 지표로 보여준다.

### 고려한 대안

1. 결과가 있으면 재분석 버튼 제공
   - 사용자가 결과가 만족스럽지 않거나 최신 첨삭 버전 기준 결과가 필요할 때 명시적으로 다시 분석할 수 있다.
   - 기존 결과 리소스를 재사용하므로 자기소개서별 최신 결과 1개 정책을 유지할 수 있다.

2. 결과가 있으면 재분석 불가
   - 결과 화면만 보여준다.
   - 기존 결과를 최신 첨삭 버전 기준으로 갱신할 수 없다.

### 선택 이유

새 PRD는 키워드 분석 결과 화면에 `AI 키워드 재분석` 버튼을 요구한다. 다만 키워드 분석 히스토리나 버전별 비교 화면은 여전히 없으므로, 재분석은 새 리소스 생성이 아니라 기존 최신 결과를 덮어쓰는 방식이 가장 단순하다.

### 트레이드오프

- 장점
  - 사용자가 명시적으로 키워드 분석을 다시 실행할 수 있다.
  - API와 화면은 계속 자기소개서별 최신 결과 1개만 다룬다.
  - 재첨삭 완료만으로 기존 결과가 사라지지 않는다.

- 단점
  - 반복 LLM 비용이 발생할 수 있다.
  - 같은 첨삭 버전에서 재분석해도 결과가 달라질 수 있다.
  - 이전 분석 결과는 보존되지 않는다.

## Decision 079: 최신 키워드 분석 응답은 화면용 자기소개서와 기준 버전 요약을 포함한다

### 결정

API-021은 모든 상태에서 `coverLetter.id`, `title`, `companyName`, `positionTitle`을 반환한다. 분석 기준이 확정된 상태에서는 `sourceReviewVersion.id`, `version`을 반환하고, `NOT_STARTED`에서는 `sourceReviewVersion=null`을 반환한다. 화면에 필요하지 않은 버전 생성 시각은 포함하지 않는다.

### 선택 이유

키워드 분석 화면은 결과와 함께 자기소개서 제목, 회사명, 직무, 분석 기준 버전을 표시한다. 화면 진입에 필요한 데이터를 API-021 하나로 제공하면 별도 상세 조회와 응답 조합이 필요 없다.

### 트레이드오프

- 장점: 키워드 화면이 한 번의 조회로 필요한 메타데이터와 결과를 얻는다.
- 단점: 키워드 분석 서비스가 자기소개서와 첨삭 버전 요약을 함께 조회해야 한다.

## Decision 088: 키워드 분석 시작은 최신 버전을 자동 선택하고 Job 정보만 반환한다

### 결정

API-020은 request body를 받지 않고 호출 시점의 최신 성공 첨삭 버전과 문항별 `finalAnswer`를 분석 입력으로 사용한다. 성공 응답은 `status=PROCESSING`과 `jobId`만 반환한다. 프론트엔드는 `jobId`로 API-016 공통 Job SSE에 연결한다.

같은 자기소개서의 키워드 분석 Job이 이미 `PENDING` 또는 `PROCESSING`이면 새 Job을 만들지 않고 기존 Job을 반환한다. 다른 종류의 LLM Job이 진행 중이면 `LLM_JOB_ALREADY_RUNNING`을 반환한다.

### 선택 이유

키워드 분석은 자기소개서별 최신 결과 하나만 유지하고 재분석도 최신 첨삭 버전을 기준으로 하므로 프론트엔드가 분석 버전을 선택할 필요가 없다. 결과는 API-021에서 자기소개서 기준으로 조회하므로 내부 키워드 분석 ID도 시작 응답에 필요하지 않다.

### 트레이드오프

- 장점: 분석 대상 버전이 일관되고 시작 요청과 응답이 단순해진다.
- 단점: 과거 첨삭 버전을 명시적으로 선택해 분석하는 기능은 제공하지 않는다.

## Decision 089: 키워드 분석 상태는 결과 조회 API를 polling한다

> Superseded by Decision 090. API-016 공통 Job SSE를 우선 사용하고 API-021 polling은 연결 실패 시 fallback으로만 사용한다.

### 결정

키워드 분석 전용 SSE는 제공하지 않고 API-021을 polling한다. `status=PROCESSING`인 동안 주기적으로 조회하고 `COMPLETED` 또는 `FAILED`가 되면 polling을 중단한다. API-021에는 `jobId`를 포함하지 않는다.

API-020의 `jobId`는 현재 polling에 사용하지 않지만 비동기 Job 식별자로 유지해 향후 Job 기반 SSE를 추가할 때 시작 API 계약을 바꾸지 않도록 한다.

### 선택 이유

키워드 결과는 중간 결과 없이 최대 20개가 한 번에 확정되고 API-021 응답도 작다. 자기소개서 ID로 결과 API를 직접 polling하면 새로고침 복구를 위해 Job ID를 별도로 저장하거나 다시 조회할 필요가 없다.

### 트레이드오프

- 장점: 현재 프론트엔드 상태 관리와 새로고침 복구가 단순하다.
- 단점: 처리 중 주기적인 HTTP 요청이 발생하며 향후 SSE 도입 시 별도 스트림 계약이 필요하다.
