# Interview API Decisions

## Decision 010: 면접 답변마다 점수, 피드백, 꼬리질문을 모두 생성한다

### 결정

AI 면접에서 사용자가 답변을 전송하면 LLM은 매번 점수, 답변 개선 피드백, 꼬리질문을 모두 생성한다.

결과 구조:

```json
{
  "role": "ASSISTANT",
  "content": "답변에서 API 설계 경험은 드러났지만 성과와 의사결정 근거가 부족합니다. 이어서, 그 API 설계에서 가장 중요하게 고려한 트레이드오프는 무엇이었나요?",
  "feedback": {
    "summary": "역할은 명확하지만 성과와 판단 근거가 부족합니다.",
    "strengths": ["담당 역할을 구체적으로 언급했습니다."],
    "improvements": ["성과 지표와 문제 해결 과정을 보강하세요."]
  },
  "score": 78,
  "followUpQuestion": "그 API 설계에서 가장 중요하게 고려한 트레이드오프는 무엇이었나요?"
}
```

### PRD 근거

- 사용자가 입력한 답변을 보고 LLM은 스트리밍 형식으로 답변을 수정해준다.
- LLM은 점수를 평가하거나 꼬리질문을 계속 이어나간다.
- 화면 우측에서 다른 질문을 클릭하면 해당 질문에 대해 새로운 채팅방에서 대화하는 형식으로 진행된다.

### 고려한 대안

1. 항상 점수, 피드백, 꼬리질문 제공
   - 사용자 답변마다 동일한 구조의 AI 응답을 생성한다.
   - 화면과 API 응답 구조가 안정적이다.

2. 항상 피드백과 꼬리질문을 제공하고, 점수는 질문 종료 시 제공
   - 실제 면접 대화 흐름에는 자연스럽지만, 질문 종료 기준을 별도로 정해야 한다.

3. LLM이 상황에 따라 점수 또는 꼬리질문을 선택
   - PRD 문구를 가장 유연하게 해석하지만, API와 화면 상태가 불안정해진다.

### 선택 이유

MVP API 명세에서는 응답 구조가 예측 가능한 것이 중요하다. 매 답변마다 점수, 피드백, 꼬리질문을 모두 생성하면 프론트엔드는 항상 같은 구조를 렌더링할 수 있고, 면접 대화 기록도 일관되게 저장할 수 있다.

### 트레이드오프

- 장점
  - API 응답 구조가 안정적이다.
  - 사용자에게 매 턴마다 명확한 평가와 다음 행동을 제공할 수 있다.
  - 대화 메시지 저장 모델이 단순하다.

- 단점
  - 매 턴마다 LLM이 생성해야 하는 정보가 많아 비용과 응답 시간이 늘 수 있다.
  - 실제 면접보다 평가 중심의 UX로 느껴질 수 있다.
  - 꼬리질문이 항상 생성되므로 대화 종료 흐름은 별도로 정의해야 한다.



## Decision 011: 면접 점수는 단일 1~100점 보조 지표로 제공한다

### 결정

AI 면접 점수는 항목별 점수나 등급이 아니라 단일 1~100점 정수로 제공한다.

면접 답변 평가에서 가장 중요한 정보는 점수가 아니라 피드백이다. 점수는 사용자가 답변 품질을 빠르게 가늠하기 위한 보조 지표로만 사용한다.

예상 구조:

```json
{
  "feedback": {
    "summary": "역할은 명확하지만 성과와 판단 근거가 부족합니다.",
    "strengths": ["담당 역할을 구체적으로 언급했습니다."],
    "improvements": ["성과 지표와 문제 해결 과정을 보강하세요."]
  },
  "score": 78
}
```

### PRD 근거

- LLM은 사용자의 답변을 기반으로 점수를 평가하거나 꼬리질문을 이어나간다.
- 사용자가 입력한 답변을 보고 LLM은 답변을 수정해준다.

### 고려한 대안

1. 1~100점 단일 점수
   - 점수는 단순한 보조 지표로 제공한다.
   - 피드백 구조를 더 중요하게 설계할 수 있다.

2. 항목별 점수 + 총점
   - 명확성, 구체성, 직무 적합성, 답변 구조 같은 항목을 나눠 점수화한다.
   - 설명력은 좋지만 점수 중심 UX가 될 가능성이 있고 API와 화면이 복잡해진다.

3. 등급형 점수
   - `A`, `B`, `C` 또는 `GOOD`, `NEEDS_IMPROVEMENT`처럼 표현한다.
   - 평가 부담은 줄지만 정량 비교가 어렵다.

### 선택 이유

Rewrite의 AI 면접에서 핵심 가치는 정밀한 채점보다 답변 개선 피드백이다. 따라서 점수 모델을 복잡하게 만들기보다 단일 점수로 단순화하고, 구체적인 개선 정보는 `feedback.summary`, `feedback.strengths`, `feedback.improvements`에 집중한다.

점수 범위와 만점이 항상 100으로 고정되므로 max 값을 DB와 API에 반복하지 않고 `score` 정수만 저장하고 반환한다.

### 트레이드오프

- 장점
  - API와 화면이 단순하다.
  - 사용자는 점수보다 피드백에 집중할 수 있다.
  - LLM 출력 구조를 안정적으로 유지하기 쉽다.

- 단점
  - 점수만으로는 어떤 부분이 부족한지 알기 어렵다.
  - 항목별 성장 추적이나 상세 분석 기능을 만들려면 나중에 점수 모델을 확장해야 한다.



## Decision 020: AI 면접 질문은 생성 요청마다 5개를 생성한다

### 결정

AI 면접 시작 시 LLM은 예상 면접 질문을 5개 생성한다.

사용자가 AI 면접 화면 우측 예상 질문 리스트 상단의 `새로운 질문 추가하기`를 실행하면, LLM은 가장 최근 첨삭 버전을 기준으로 면접 질문 5개를 추가 생성한다.

질문 구성:

```text
COVER_LETTER_BASED: 3개
TECHNICAL: 2개
```

### PRD 근거

- 모의면접 시작 시 LLM이 해당 자기소개서를 바탕으로 예상 질문 리스트 혹은 기술 면접 예상 질문을 만들어 화면 우측에 보여준다.
- 예상 질문 리스트 상단의 `새로운 질문 추가하기` 버튼을 누르면 가장 최근 버전의 자기소개서를 바탕으로 5개의 면접 질문 리스트를 만들어준다.
- 사용자는 화면 우측에서 예상 질문을 클릭해 질문별 대화방에서 면접 연습을 진행한다.

### 고려한 대안

1. 생성 요청마다 5개: 자기소개서 기반 3개 + 기술 질문 2개
   - MVP에 적당하고 사용자가 부담 없이 시작할 수 있다.
   - 질문별 대화 품질에 집중할 수 있다.

2. 생성 요청마다 10개: 자기소개서 기반 6개 + 기술 질문 4개
   - 더 풍부한 면접 연습이 가능하다.
   - 첫 생성 비용과 화면 부담이 늘어난다.

3. 사용자가 질문 개수 선택
   - 유연하지만 API와 UI 옵션이 늘어 MVP에는 과하다.

### 선택 이유

AI 면접은 질문을 많이 만드는 것보다 질문별 대화 품질이 중요하다. 한 번의 생성 요청에서 우측 질문 리스트가 과도하게 길 필요는 없으므로, 요청마다 5개가 적합하다. 추가 연습이 필요하면 사용자가 명시적으로 `새로운 질문 추가하기`를 실행해 5개씩 확장한다.

### 트레이드오프

- 장점
  - 생성 비용과 응답 시간을 통제하기 쉽다.
  - 사용자가 시작하기 부담스럽지 않다.
  - 자기소개서 기반 질문과 기술 질문을 모두 포함할 수 있다.
  - 사용자가 원할 때 질문을 5개씩 추가할 수 있다.

- 단점
  - 직무별 심화 질문이 부족할 수 있다.
  - 사용자가 더 많은 질문을 원할 경우 추가 생성 기능이 필요할 수 있다.



## Decision 026: 자기소개서당 AI 면접 세션은 하나만 유지한다

### 결정

MVP에서는 자기소개서당 AI 면접 세션을 하나만 유지한다.

AI 면접 페이지는 현재 면접 세션 상태에 따라 화면을 결정한다.

```text
세션 없음: 모의면접 시작하기 화면
QUESTION_GENERATING: 초기 질문 생성 진행 화면
ACTIVE: 기존 대화 화면과 질문 리스트
FAILED: 실패 안내와 다시 시작하기 또는 재시도 버튼
```

기존 면접 세션이 있는 상태에서 사용자가 `새로운 질문 추가하기`를 실행하면 새 면접 세션을 만들지 않고, 기존 세션에 최신 첨삭 버전 기준 면접 질문 5개를 추가한다.

API 형태:

```http
GET  /cover-letters/{coverLetterId}/interview
POST /cover-letters/{coverLetterId}/interviews
POST /interviews/{interviewSessionId}/questions
```

`GET /cover-letters/{coverLetterId}/interview`는 현재 면접 세션이 있으면 세션 정보를 반환하고, 없으면 `interviewSession: null`을 반환한다.

`POST /cover-letters/{coverLetterId}/interviews`는 면접 세션이 없을 때 새 세션과 초기 질문 생성 Job을 만든다. 이미 `ACTIVE` 또는 `QUESTION_GENERATING` 세션이 있으면 기존 세션을 반환하고 초기 질문 생성 Job을 새로 만들지 않는다. 기존 세션이 `FAILED`이면 같은 세션을 재사용해 다시 `QUESTION_GENERATING`으로 전환하고 새 초기 질문 생성 Job을 시작한다.

`POST /interviews/{interviewSessionId}/questions`는 기존 면접 세션에 새 질문 생성 Job을 만들고, 성공 시 질문 5개를 기존 질문 목록 뒤에 추가한다.

### PRD 근거

- `AI 면접` 첫 화면 중앙에는 `모의면접 시작하기` 버튼이 있다.
- 시작 버튼을 누르면 대화창과 예상 질문 리스트가 나온다.
- 예상 질문 리스트 상단에는 `새로운 질문 추가하기` 버튼이 있다.
- PRD에는 면접 세션 히스토리나 여러 세션 선택 기능이 없다.

### 고려한 대안

1. 자기소개서당 면접 세션 1개만 유지
   - 한 번 시작한 뒤에는 기존 세션을 계속 사용한다.
   - 추가 질문은 기존 세션에 누적한다.
   - API와 화면 상태가 단순하다.

2. 시작할 때마다 새 면접 세션 생성
   - 여러 번 연습한 기록을 남길 수 있다.
   - 세션 목록과 선택 UI가 필요하다.

3. 기존 세션 재사용 + 명시적 재시작 API
   - 기본은 단순하고 확장성도 있다.
   - 하지만 MVP에는 API와 UI가 하나 더 늘어난다.

### 선택 이유

PRD에는 면접 히스토리나 여러 면접 세션 관리가 없다. 사용자가 한 번 면접을 시작했다면 이후에는 시작 버튼 페이지보다 기존 질문 리스트와 대화 화면으로 바로 들어가는 것이 자연스럽다. 새 요구사항의 `새로운 질문 추가하기`도 새 세션을 만드는 기능이 아니라 기존 질문 리스트를 확장하는 기능으로 해석하는 것이 세션 1개 정책과 가장 잘 맞는다.

### 트레이드오프

- 장점
  - AI 면접 화면 진입 UX가 단순하다.
  - 세션 목록, 재시작, 히스토리 UI가 필요 없다.
  - 질문별 대화방 상태를 안정적으로 유지할 수 있다.
  - 기존 대화를 유지하면서 최신 첨삭 기준 질문을 추가할 수 있다.

- 단점
  - 여러 회차 연습 기록을 비교할 수 없다.
  - 질문이 계속 누적되므로 목록이 길어질 수 있다.



## Decision 027: 재첨삭 후에도 기존 AI 면접 세션은 유지한다

### 결정

자기소개서 재첨삭으로 새 `ReviewVersion`이 생성되어도 기존 AI 면접 세션은 유지한다.

면접 세션은 최초 질문 세트를 생성할 때 기준이 된 첨삭 버전을 `initialSourceReviewVersionId`로 기록한다. 재첨삭이 완료되어 최신 첨삭 버전이 바뀌어도 기존 면접 세션의 질문 리스트와 대화방은 자동 갱신하지 않는다.

다만 사용자가 `새로운 질문 추가하기`를 명시적으로 실행하면, 기존 세션에 최신 첨삭 버전 기준 질문 5개를 추가한다. 이때 기존 질문과 대화방은 변경하지 않는다.

예상 구조:

```json
{
  "interviewSessionId": "is_01HZ...",
  "initialSourceReviewVersionId": "rv_01HZ...",
  "questions": [
    {
      "interviewQuestionId": "iq_01HZ...",
      "sourceReviewVersionId": "rv_01HZ..."
    }
  ]
}
```

### PRD 근거

- AI 면접은 사용자가 등록하고 LLM에 의해 첨삭된 자기소개서를 바탕으로 예상 질문 리스트를 생성한다.
- PRD에는 재첨삭 후 기존 면접 질문을 자동 갱신한다는 요구가 없다.
- PRD는 `새로운 질문 추가하기`를 통해 가장 최근 버전의 자기소개서를 바탕으로 5개의 면접 질문 리스트를 추가 생성하도록 요구한다.
- PRD에는 면접 세션 재시작이나 여러 세션 관리 기능이 없다.

### 고려한 대안

1. 기존 면접 세션 유지
   - 최초 질문 세트의 기준 첨삭 버전은 `initialSourceReviewVersionId`로 기록한다.
   - 각 질문의 실제 생성 기준 첨삭 버전은 `InterviewQuestion.sourceReviewVersionId`로 기록한다.
   - 대화 기록의 기준이 안정적이다.
   - 새 질문 추가 요청은 최신 첨삭 버전 기준 질문을 기존 세션 뒤에 추가한다.

2. 재첨삭 완료 시 기존 면접 세션 무효화
   - 최신 첨삭 버전에 맞는 면접 질문을 만들 수 있다.
   - 하지만 기존 대화 기록이 사라지거나 상태 전이가 복잡해진다.

3. 재첨삭 완료 시 기존 세션을 최신 버전으로 자동 갱신
   - 항상 최신 첨삭 기준 면접을 제공할 수 있다.
   - 하지만 이미 생성된 질문과 대화의 기준이 바뀌어 데이터 정합성이 나빠진다.

### 선택 이유

면접 질문과 대화는 생성 당시의 자기소개서/첨삭 버전을 기준으로 해석되어야 한다. 재첨삭 후 자동으로 기존 세션을 변경하면 과거 질문과 답변의 기준이 불명확해진다. 따라서 기존 질문과 대화는 유지한다. 최신 첨삭 기준 질문이 필요하면 사용자가 `새로운 질문 추가하기`를 실행하고, 새로 생성된 질문에만 최신 `sourceReviewVersionId`를 기록한다.

### 트레이드오프

- 장점
  - 면접 질문과 대화 기록의 기준이 안정적이다.
  - 재첨삭이 기존 면접 진행 상태를 깨지 않는다.
  - 최신 첨삭 기준 질문을 명시적으로 추가할 수 있다.

- 단점
  - 재첨삭 후에도 기존 면접은 이전 첨삭 버전을 기준으로 유지된다.
  - 한 면접 세션 안에 서로 다른 `sourceReviewVersionId`를 가진 질문이 함께 존재할 수 있다.



## Decision 030: 면접 답변은 최대 2000자로 제한한다

### 결정

AI 면접에서 사용자가 입력하는 답변 `content`는 최대 2000자로 제한한다.

이 제한은 자기소개서 문항 답변의 최대 5000자 제한과 별개다.

예상 validation:

```text
content: 필수, 최대 2000자
```

### PRD 근거

- 사용자는 AI 면접 화면 하단 답변 입력란에 답변을 입력한다.
- 사용자가 입력한 답변을 보고 LLM은 피드백과 꼬리질문을 이어간다.

### 고려한 대안

1. 1000자
   - 실제 면접 답변처럼 짧고 핵심적으로 답하게 유도한다.
   - 다만 STAR 구조로 충분히 설명하기에는 부족할 수 있다.

2. 2000자
   - 구체적인 답변을 허용하면서 과도한 장문을 막는다.
   - 면접 연습 답변으로 현실적인 상한이다.

3. 5000자
   - 자기소개서 답변과 같은 상한이다.
   - 하지만 면접 답변으로는 너무 길고 LLM 비용과 품질 관리에 불리하다.

### 선택 이유

면접 답변은 자기소개서 본문보다 짧고 구두 답변에 가까워야 한다. 동시에 STAR 구조로 상황, 행동, 결과를 설명할 수 있어야 하므로 1000자보다 여유 있는 2000자가 적절하다.

### 트레이드오프

- 장점
  - 면접 답변이 과도하게 길어지는 것을 막는다.
  - LLM 피드백 비용과 응답 품질을 관리하기 쉽다.
  - 사용자가 충분히 구체적인 답변을 작성할 수 있다.

- 단점
  - 매우 긴 경험 서술은 줄여야 한다.
  - 실제 음성 면접보다 긴 답변도 허용될 수 있다.



## Decision 031: 면접 꼬리질문은 피드백과 같은 assistant 메시지에 저장한다

### 결정

AI 면접에서 사용자 답변 1개에 대해 assistant 메시지 1개를 생성한다.

assistant 메시지는 피드백, 점수, 꼬리질문을 모두 포함한다. 꼬리질문을 별도 assistant 메시지로 분리 저장하지 않는다.

예상 구조:

```json
{
  "role": "ASSISTANT",
  "content": "답변 피드백과 다음 꼬리질문을 포함한 문장",
  "feedback": {
    "summary": "역할은 명확하지만 성과와 판단 근거가 부족합니다.",
    "strengths": ["담당 역할을 구체적으로 언급했습니다."],
    "improvements": ["성과 지표와 문제 해결 과정을 보강하세요."]
  },
  "score": 78,
  "followUpQuestion": "그 API 설계에서 가장 중요하게 고려한 트레이드오프는 무엇이었나요?"
}
```

### PRD 근거

- 사용자가 입력한 답변을 보고 LLM은 스트리밍 형식으로 답변을 수정해주고 꼬리질문을 이어나간다.
- AI 면접은 chat gpt 대화창 같은 대화창에서 진행된다.

### 고려한 대안

1. 한 assistant 메시지에 피드백과 꼬리질문을 함께 저장
   - 사용자 답변 1개에 AI 응답 1개가 생긴다.
   - 메시지 조회, 저장, 스트리밍 구조가 단순하다.

2. 피드백 메시지와 꼬리질문 메시지를 분리 저장
   - 채팅 UI에서는 자연스러울 수 있다.
   - 하지만 사용자 답변 1개에 assistant 메시지 2개가 생겨 저장, 스트리밍, 조회가 복잡해진다.

### 선택 이유

MVP에서는 사용자 답변 1개에 대한 평가 결과를 하나의 assistant 메시지로 다루는 것이 단순하다. 이미 매 답변마다 점수, 피드백, 꼬리질문을 모두 생성하기로 했으므로 같은 메시지에 저장하는 것이 자연스럽다.

### 트레이드오프

- 장점
  - 메시지 모델이 단순하다.
  - 사용자 답변과 AI 평가 메시지의 대응 관계가 명확하다.
  - 스트리밍 완료 시 하나의 assistant 메시지만 저장하면 된다.

- 단점
  - 꼬리질문만 별도 채팅 말풍선으로 다루기 어렵다.
  - 향후 더 자연스러운 채팅 UI를 위해 메시지 분리 정책을 재검토할 수 있다.



## Decision 067: AI 면접 답변 피드백은 완료 후 assistant 메시지만 저장한다

### 결정

AI 면접 답변 피드백 Job(`INTERVIEW_MESSAGE_FEEDBACK`)은 진행 중 assistant 메시지를 미리 생성하지 않는다.

사용자 답변을 저장한 뒤 LLM Job을 시작하고, Job이 성공적으로 완료되면 assistant 메시지 1개를 저장한다.

적용 API:

```http
POST /interview-threads/{threadId}/messages
GET  /interview-threads/{threadId}/messages
GET  /llm-jobs/{jobId}/stream
```

저장 정책:

```text
사용자 답변 전송:
  USER 메시지 저장
  INTERVIEW_MESSAGE_FEEDBACK Job 생성
  jobId 반환

피드백 생성 중:
  assistant 메시지 미생성
  면접 피드백용 partialResult 미저장
  현재 SSE 연결 화면에만 delta 표시

피드백 생성 성공:
  assistant 메시지 1개 저장
  feedback, score, followUpQuestion 포함

피드백 생성 실패:
  assistant 메시지 저장하지 않음
  LlmJob.status=FAILED
```

화면 재진입 정책:

```text
PROCESSING:
  진행 상태만 복구
  이전에 흘러간 피드백 delta는 복구하지 않음

COMPLETED:
  GET /interview-threads/{threadId}/messages로 저장된 assistant 메시지 조회
```

### PRD 근거

- AI 면접에서 사용자가 답변을 전송하면 LLM은 피드백, 점수, 꼬리질문을 생성한다.
- 사용자 답변 1개에 대해 assistant 메시지 1개를 저장하기로 했다.
- 면접 메시지는 대화 기록으로 남는 데이터이므로 미완성 assistant 메시지가 목록에 섞이면 조회와 표시가 복잡해진다.

### 고려한 대안

1. 완료 후 assistant 메시지만 저장
   - 메시지 목록에는 완성된 assistant 메시지만 남는다.
   - 저장 모델이 단순하다.
   - 중간 재진입 시 이전 delta는 복구하지 못한다.

2. 진행 중 assistant 메시지를 먼저 만들고 partial content를 갱신
   - 재진입 시 지금까지 생성된 피드백을 복구할 수 있다.
   - 하지만 `PROCESSING` assistant 메시지 상태, 실패 시 미완성 메시지 처리, 조회 필터링 정책이 필요하다.

3. 첨삭처럼 서버 메모리 partialResult로 복구
   - 진행 중 텍스트 복구가 가능하다.
   - 하지만 면접 메시지용 partial 구조가 추가되고, 첨삭보다 짧은 응답에 비해 복잡도가 커진다.

### 선택 이유

면접 피드백은 대화 메시지 단위의 응답이고, 최종적으로 저장되는 assistant 메시지가 사용자에게 중요한 기록이다. MVP에서는 진행 중 복구보다 메시지 저장 모델의 단순성과 일관성이 더 중요하다.

따라서 진행 중에는 SSE로 현재 연결된 화면에만 delta를 보여주고, 저장은 완료 후 assistant 메시지 1개로 확정한다.

### 트레이드오프

- 장점
  - 메시지 목록에 미완성 assistant 메시지가 섞이지 않는다.
  - 실패 시 assistant 메시지를 남기지 않아 대화 기록이 깔끔하다.
  - 저장/조회/정렬 정책이 단순하다.

- 단점
  - 사용자가 피드백 생성 중 화면을 이탈하면 완료 전까지 생성된 delta를 복구할 수 없다.
  - 진행 중 재진입 화면에서는 스트리밍 텍스트 UX가 제한된다.
  - 향후 긴 면접 피드백이나 복구 UX가 중요해지면 partial 저장 정책을 다시 검토해야 한다.



## Decision 073: 면접 질문과 질문별 대화방은 함께 생성한다

### 결정

면접 질문을 저장할 때 각 질문의 `InterviewThread`를 같은 transaction에서 함께 저장한다. 질문과 thread는 1:1 관계이며, 생성된 모든 질문은 반드시 하나의 thread를 가진다.

최초 면접 질문은 `InterviewQuestion.question`으로 관리한다. 질문 본문을 최초 `ASSISTANT` 메시지로 중복 저장하지 않으며, `InterviewMessage`는 사용자가 답변을 전송한 시점부터 저장한다.

API-028 `POST /interviews/{interviewSessionId}/threads`는 사용하지 않는다. 클라이언트는 API-026 질문 목록에서 받은 필수 `threadId`로 질문별 대화에 접근한다.

### PRD 근거

- 사용자는 화면 우측의 예상 질문을 클릭해 질문별 독립 대화방에서 면접 연습을 진행한다.
- 모든 예상 질문은 동일한 방식으로 답변과 피드백 대화를 시작할 수 있어야 한다.
- 질문을 클릭하는 행위 자체에는 별도 생성 비용이나 LLM 호출이 필요하지 않다.

### 고려한 대안

1. 질문 생성 시 thread 동시 생성
   - 질문과 대화방의 1:1 관계가 항상 성립한다.
   - 질문 클릭 시 별도 상태 변경 요청이 필요 없다.
   - 질문 본문은 `InterviewQuestion`에만 저장할 수 있다.

2. 질문을 처음 클릭할 때 thread 지연 생성
   - 사용하지 않는 질문의 thread row를 만들지 않는다.
   - 생성 API, 멱등성, 동시 클릭 경쟁 처리가 추가로 필요하다.
   - 질문 목록의 `threadId`가 nullable이 된다.

3. 최초 질문을 `ASSISTANT` 메시지로 저장
   - 일반적인 채팅 메시지 모델과 유사하다.
   - 같은 질문 본문이 `InterviewQuestion`과 `InterviewMessage`에 중복 저장된다.

### 선택 이유

MVP에서는 모든 생성 질문이 바로 답변 가능한 대상이며 thread row의 저장 비용도 작다. 질문 생성과 thread 생성을 한 transaction으로 묶으면 별도 생성 API와 경쟁 상태를 제거하고, API-026의 응답 계약도 단순하게 유지할 수 있다.

최초 질문은 이미 `InterviewQuestion`에 영속화되므로 message로 복제하지 않는다. 이후 메시지에는 사용자 답변과 그 답변에 대한 AI 피드백만 저장한다.

### 트레이드오프

- 장점
  - 질문과 thread 사이의 필수 1:1 불변식이 명확하다.
  - 질문 클릭 시 추가 API 호출과 중복 생성 처리가 필요 없다.
  - 질문 본문의 중복 저장을 피할 수 있다.

- 단점
  - 사용자가 선택하지 않은 질문에도 thread row가 생성된다.
  - 질문 생성 transaction에서 저장해야 하는 row 수가 늘어난다.
