# Cover Letter API Decisions

## Decision 003: 임시저장 자기소개서도 목록에 노출한다

### 결정

사용자가 등록 step1, step2, step3에서 임시저장한 자기소개서도 `내 자기소개서 목록`에 노출한다.

목록 카드의 상태는 AI 첨삭 여부만이 아니라 자기소개서 작성 및 첨삭 진행 상태를 표현한다.

상태:

```text
DRAFT
REVIEWING
REVIEWED
REVIEW_FAILED
```

API 형태:

```http
GET  /cover-letters?page=1&size=9&status=DRAFT
POST /cover-letters
PUT  /cover-letters/{coverLetterId}/basic-info
PUT  /cover-letters/{coverLetterId}/preferences
PUT  /cover-letters/{coverLetterId}/questions
POST /cover-letters/{coverLetterId}/submit
```

### PRD 근거

- 등록 step1, step2, step3에 모두 `임시저장` 버튼이 존재한다.
- 등록 완료 후 `내 자기소개서 목록` 페이지에 자기소개서가 추가된다.
- 목록 카드에는 AI 첨삭 여부가 표시된다.

### 고려한 대안

1. 임시저장도 목록에 노출
   - 목록에서 작성 중인 자기소개서를 다시 열어 이어서 작성할 수 있다.
   - 목록 상태가 `작성 중`, `첨삭 중`, `첨삭 완료`, `첨삭 실패`처럼 확장된다.

2. 완료 제출한 자기소개서만 목록에 노출
   - 목록은 첨삭 대상 문서만 보여줘 단순하다.
   - 하지만 임시저장한 문서를 사용자가 어디에서 다시 찾는지 별도 UX와 API가 필요하다.

### 선택 이유

임시저장 기능을 제공하려면 사용자가 저장한 문서를 다시 찾고 이어서 작성할 수 있어야 한다. PRD에 별도의 임시저장함이 없으므로 기존 `내 자기소개서 목록`에 노출하는 것이 가장 자연스럽다.

### 트레이드오프

- 장점
  - 임시저장 기능의 사용자 접근 경로가 명확하다.
  - 목록 하나로 작성 중, 첨삭 중, 첨삭 완료 문서를 모두 관리할 수 있다.
  - API가 별도의 임시저장함 리소스를 만들지 않아도 된다.

- 단점
  - 목록 카드 상태가 PRD의 `첨삭 중`, `첨삭 완료`보다 확장된다.
  - 목록에서 `DRAFT` 항목 클릭 시 등록 step으로 이동하고, `REVIEWING` 또는 `REVIEWED` 항목 클릭 시 AI 첨삭 페이지로 이동하는 라우팅 규칙이 필요하다.



## Decision 016: 자기소개서 삭제는 Soft delete로 처리한다

### 결정

자기소개서 삭제는 hard delete가 아니라 soft delete로 처리한다.

삭제 요청 시 `CoverLetter.deletedAt`을 기록하고, 내 자기소개서 목록과 상세 조회에서는 삭제된 자기소개서를 기본적으로 제외한다. 삭제된 자기소개서에 연결된 질문, 첨삭 버전, 키워드 분석, 면접 데이터는 물리 삭제하지 않는다.

진행 중인 LLM Job이 있는 자기소개서가 삭제되면 해당 Job은 `CANCELED` 상태로 전환한다.

API 형태:

```http
DELETE /cover-letters/{coverLetterId}
```

응답:

```json
{
  "success": true,
  "deletedAt": "2026-06-20T15:00:00"
}
```

### PRD 근거

- AI 첨삭 화면 좌측에 해당 자기소개서 삭제 버튼이 존재한다.
- 자기소개서는 질문, 첨삭 버전, 키워드 분석, AI 면접과 연결된다.

### 고려한 대안

1. Hard delete
   - 삭제 즉시 자기소개서와 연결 데이터를 물리 삭제한다.
   - 구현과 저장소 관리는 단순하지만, 실수로 삭제한 데이터 복구가 어렵고 진행 중 Job 처리가 까다롭다.

2. Soft delete
   - `deletedAt`을 기록하고 사용자 화면에서 숨긴다.
   - 연결 데이터는 보존한다.
   - 복구, 감사, 진행 중 Job 취소 처리에 유리하다.

### 선택 이유

자기소개서는 사용자가 직접 작성한 중요한 데이터이고, 첨삭 버전과 면접 데이터가 연결된다. 물리 삭제보다 soft delete가 데이터 보호와 운영 안정성 측면에서 더 안전하다.

### 트레이드오프

- 장점
  - 실수 삭제나 장애 상황에서 복구 여지를 남길 수 있다.
  - 연결 데이터의 참조 무결성을 유지하기 쉽다.
  - 진행 중 LLM Job을 취소 상태로 전환하는 정책과 잘 맞는다.

- 단점
  - 모든 조회 API에서 `deletedAt` 필터를 적용해야 한다.
  - 저장소에 삭제된 데이터가 계속 남는다.
  - 개인정보 삭제 요청 같은 별도 요구가 생기면 물리 삭제 정책을 추가해야 한다.



## Decision 023: 제출 후 원본 자기소개서는 수정할 수 없다

### 결정

자기소개서 제출 후에는 원본 자기소개서 정보를 수정할 수 없다.

수정 불가 범위:

```text
basic-info
preferences
questions
originalAnswer
```

수정 가능 범위:

```text
finalAnswer
```

즉, `DRAFT` 상태에서만 등록 step1~step3 저장 API를 사용할 수 있다. `REVIEWING`, `REVIEWED`, `REVIEW_FAILED` 상태에서는 원본 수정 API를 호출하면 `CONFLICT`를 반환한다.

### PRD 근거

- 등록 step4는 지금까지 작성한 내용을 모두 확인하는 페이지이며 수정이 불가능하다.
- 완료 버튼을 누르면 목록에 자기소개서가 추가되고 LLM 첨삭이 시작된다.
- AI 첨삭 화면에서는 사용자가 AI 리포트를 참고하여 `최종 작성본`을 직접 작성한다.

### 고려한 대안

1. 제출 후 원본 수정 불가
   - 첨삭 버전과 원본 기준이 안정적이다.
   - 하지만 회사명이나 문항 오타 수정이 어렵다.

2. 제출 후에도 원본 수정 가능, 수정 시 기존 첨삭 무효화
   - 사용자는 자유롭게 수정할 수 있다.
   - 하지만 기존 첨삭, 키워드 분석, 면접 결과의 기준이 흔들린다.

3. 제출 후에는 최종 작성본만 수정 가능
   - 원본 질문, 답변, 회사 정보는 잠근다.
   - AI 첨삭 화면의 최종 작성본만 저장할 수 있다.

### 선택 이유

Rewrite의 버전 히스토리는 AI 첨삭 결과를 기준으로 관리한다. 제출 후 원본을 수정하면 기존 첨삭 버전, 키워드 분석, 면접 결과가 어떤 원본을 기준으로 생성되었는지 불명확해진다. 따라서 제출 후에는 원본을 잠그고 최종 작성본만 수정하는 것이 데이터 정합성에 유리하다.

### 트레이드오프

- 장점
  - 첨삭 버전의 기준 데이터가 안정적으로 유지된다.
  - 키워드 분석과 면접 결과의 source 기준이 명확하다.
  - API 상태 전이가 단순하다.

- 단점
  - 제출 후 회사명, 공고 링크, 문항 오타를 직접 고칠 수 없다.
  - 원본 수정을 지원하려면 향후 `복제해서 새 자기소개서로 편집` 같은 기능이 필요할 수 있다.



## Decision 025: 삭제된 자기소개서 복구 API는 제공하지 않는다

### 결정

MVP에서는 삭제된 자기소개서를 사용자가 직접 복구할 수 있는 API를 제공하지 않는다.

Soft delete는 사용자-facing 복구 기능이 아니라 내부 안전장치, 감사, 운영 대응을 위한 보존 정책으로 사용한다.

제공하지 않는 API:

```http
POST /cover-letters/{coverLetterId}/restore
GET  /cover-letters/deleted
```

### PRD 근거

- PRD에는 자기소개서 삭제 버튼은 있지만 삭제 목록이나 복구 기능은 없다.
- 현재 주요 흐름은 자기소개서 등록, 첨삭, 키워드 분석, AI 면접이다.

### 고려한 대안

1. 복구 API 제공 안 함
   - Soft delete는 내부 안전장치와 운영 보존 용도로만 사용한다.
   - MVP API와 사용자 UX가 단순하다.

2. 복구 API 제공
   - `POST /cover-letters/{coverLetterId}/restore` 같은 API를 제공한다.
   - 실수 삭제 복구가 가능하지만 삭제 목록, 복구 UI, 권한 정책이 추가된다.

### 선택 이유

MVP 범위에서는 삭제 복구가 핵심 사용자 흐름이 아니다. Soft delete는 데이터 보호와 운영 안정성을 위해 유지하되, 사용자-facing 복구 API는 추후 필요가 확인되면 추가한다.

### 트레이드오프

- 장점
  - MVP API 범위가 단순해진다.
  - 삭제 목록과 복구 UI를 만들 필요가 없다.
  - soft delete의 운영상 장점은 유지한다.

- 단점
  - 사용자가 실수로 삭제한 자기소개서를 직접 복구할 수 없다.
  - 운영자 복구가 필요하면 별도 내부 도구나 DB 대응이 필요하다.



## Decision 032: 최초 첨삭 실패만 CoverLetter.status를 REVIEW_FAILED로 변경한다

### 결정

첨삭 Job 실패 시 `CoverLetter.status` 전이는 최초 첨삭과 재첨삭을 구분한다.

상태 전이:

```text
최초 첨삭 실패: REVIEWING -> REVIEW_FAILED
재첨삭 실패: REVIEWED 유지, 실패한 LLM Job만 FAILED
```

재첨삭 실패는 기존 성공 첨삭 버전을 무효화하지 않는다.

### PRD 근거

- 목록 카드에는 AI 첨삭 여부가 표시된다.
- 최초 등록 완료 후 LLM이 첨삭하는 동안 `첨삭 중`으로 표기된다.
- 재첨삭 시 새 버전이 생성되어 저장된다.

### 고려한 대안

1. 첨삭 실패 시 항상 `REVIEW_FAILED`
   - 실패 상태를 목록에서 명확히 보여줄 수 있다.
   - 하지만 재첨삭 실패 시 기존 성공 버전이 있는데도 전체 자기소개서가 실패처럼 보인다.

2. 최초 첨삭 실패만 `REVIEW_FAILED`, 재첨삭 실패는 기존 상태 유지
   - 기존 성공 첨삭 결과를 계속 사용할 수 있다.
   - 실패한 재첨삭은 LLM Job의 `FAILED` 상태로만 표현한다.

### 선택 이유

재첨삭 실패는 기존 첨삭 결과를 무효화하지 않는다. 이미 `REVIEWED` 상태이고 성공한 `ReviewVersion`이 있다면, 재첨삭 실패 때문에 자기소개서 전체 상태를 실패로 바꾸는 것은 UX상 부정확하다.

### 트레이드오프

- 장점
  - 기존 성공 첨삭 결과를 계속 사용할 수 있다.
  - 목록 상태가 실제 사용 가능 여부를 더 정확히 표현한다.
  - 실패한 재첨삭은 Job 단위로만 추적하면 된다.

- 단점
  - 최초 첨삭 실패와 재첨삭 실패의 처리 규칙이 다르다.
  - 재첨삭 실패 알림이나 모달 표시 정책은 프론트에서 별도로 처리해야 한다.



## Decision 035: 공고 링크는 URL 형식만 검증한다

### 결정

`jobPostingUrl`은 선택 입력값이며, 서버는 최대 길이와 URL 형식만 검증한다.

서버는 공고 링크가 실제로 접근 가능한지, 로그인 없이 열리는지, 채용공고가 만료되지 않았는지, 특정 채용 플랫폼에서 차단하지 않는지는 검증하지 않는다.

적용 API:

```http
POST  /cover-letters
PUT   /cover-letters/{coverLetterId}/basic-info
```

Validation:

```text
jobPostingUrl: 선택, trim 후 최대 500자, URL 형식
```

### PRD 근거

- 등록 step1에서 `지원 공고 링크`를 입력한다.
- PRD는 공고 링크를 기반으로 서버가 실시간 크롤링하거나 접근 가능 여부를 확인해야 한다고 요구하지 않는다.
- AI 첨삭의 주요 입력은 회사명, 직무명, 우대사항, 자기소개서 문항/답변이다.

### 고려한 대안

1. URL 형식만 검증
   - 사용자가 입력한 값이 URL로 파싱 가능한지만 확인한다.
   - 외부 채용 사이트의 차단, 로그인, 만료, 네트워크 상태에 API 성공 여부가 의존하지 않는다.

2. 서버가 실제 접근 가능 여부까지 검증
   - 잘못된 링크를 조기에 잡을 수 있다.
   - 하지만 채용 플랫폼마다 로그인, bot 차단, 지역 제한, 만료 정책이 달라 정상 링크도 실패할 수 있다.

3. 검증하지 않음
   - 구현은 가장 단순하다.
   - 하지만 명백히 URL이 아닌 문자열이 저장될 수 있어 데이터 품질이 낮아진다.

### 선택 이유

공고 링크는 부가 정보에 가깝고, 외부 사이트의 접근 가능 여부는 Rewrite 서버가 안정적으로 책임지기 어렵다. 서버가 도달성 검증까지 수행하면 사용자 입력 저장이 외부 채용 플랫폼의 상태에 흔들린다. 따라서 MVP에서는 URL 형식만 검증한다.

### 트레이드오프

- 장점
  - API 응답이 외부 사이트 상태에 의존하지 않는다.
  - 구현과 운영이 단순하다.
  - private, 로그인 필요, 만료 예정 공고 링크도 사용자가 참고용으로 저장할 수 있다.

- 단점
  - 실제로 열리지 않는 링크가 저장될 수 있다.
  - 링크 만료 여부나 접근 제한 여부는 사용자나 프론트엔드 UX에서 별도로 확인해야 한다.



## Decision 042: 원본 답변도 앞뒤 공백을 trim한 뒤 검증하고 저장한다

> Superseded by Decision 096. 비어 있지 않은 값의 trim·최대 길이 정책은 유지하지만, DRAFT의 빈 값은 오류 대신 `null`로 임시저장하고 제출 시 필수 검증한다.

### 결정

등록 step3의 원본 답변 `originalAnswer`도 서버에서 앞뒤 공백을 제거한 뒤 길이를 검증한다.

서버는 trim된 값을 저장한다.

적용 API:

```http
PUT /cover-letters/{coverLetterId}/questions
```

검증 순서:

```text
1. originalAnswer 앞뒤 공백 제거
2. trim된 originalAnswer가 Unicode code point 기준 1~5000자인지 검증
3. trim된 originalAnswer 저장
```

예시:

```text
"  제가 지원한 이유는...  " -> "제가 지원한 이유는..."
"   " -> VALIDATION_ERROR
```

### PRD 근거

- 등록 step3에서 사용자는 자기소개서 질문과 답변을 입력한다.
- 원본 답변은 이후 AI 첨삭, diff, 최종 작성본, 키워드 분석, AI 면접의 기준 데이터가 된다.
- 자기소개서 본문에서 앞뒤 공백은 의미 있는 내용으로 보기 어렵다.

### 고려한 대안

1. 원본 답변도 앞뒤 공백 trim 후 1~5000자 검증
   - 최종 작성본 정책과 일관된다.
   - 공백만 있는 원본 답변 저장을 막을 수 있다.

2. 원본 답변은 원문 그대로 저장
   - 사용자가 입력한 문자열을 완전히 보존한다.
   - 하지만 공백만 있는 답변 처리와 글자 수 기준이 애매해진다.

### 선택 이유

원본 답변은 AI 첨삭과 후속 기능의 기준 데이터다. 원본 답변에 공백만 저장되거나 불필요한 앞뒤 공백이 포함되면 이후 diff, 글자 수, LLM 입력 품질이 흔들린다. 최종 작성본과 같은 trim 정책을 사용해 데이터 정합성을 맞춘다.

### 트레이드오프

- 장점
  - 원본 답변과 최종 작성본의 문자열 정규화 정책이 일관된다.
  - 공백만 있는 자기소개서 답변 저장을 방지할 수 있다.
  - LLM 입력 데이터 품질이 좋아진다.

- 단점
  - 사용자가 의도적으로 앞뒤 공백을 넣어도 보존되지 않는다.
  - 원문 입력을 완전 그대로 보관하는 감사 요구가 생기면 별도 raw value 저장 정책이 필요하다.



## Decision 043: 질문 문구도 앞뒤 공백을 trim한 뒤 검증하고 저장한다

> Superseded by Decision 096. 비어 있지 않은 값의 trim·최대 길이 정책은 유지하지만, DRAFT의 빈 값은 오류 대신 `null`로 임시저장하고 제출 시 필수 검증한다.

### 결정

등록 step3의 질문 문구 `question`도 서버에서 앞뒤 공백을 제거한 뒤 길이를 검증한다.

서버는 trim된 값을 저장한다.

적용 API:

```http
PUT /cover-letters/{coverLetterId}/questions
```

검증 순서:

```text
1. question 앞뒤 공백 제거
2. trim된 question이 Unicode code point 기준 1~300자인지 검증
3. trim된 question 저장
```

예시:

```text
"  지원 동기를 작성해주세요.  " -> "지원 동기를 작성해주세요."
"   " -> VALIDATION_ERROR
```

### PRD 근거

- 등록 step3에서 사용자는 자기소개서 질문과 답변을 입력한다.
- 질문 문구는 AI 첨삭 상세 화면, diff 기준 문항, 키워드 분석, AI 면접 질문 생성의 기준 데이터다.
- 질문 문구의 앞뒤 공백은 사용자에게 의미 있는 내용으로 보기 어렵다.

### 고려한 대안

1. 질문 문구도 앞뒤 공백 trim 후 1~300자 검증
   - 원본 답변과 최종 작성본 정책과 일관된다.
   - 공백만 있는 질문 저장을 막을 수 있다.

2. 질문 문구는 원문 그대로 저장
   - 사용자가 입력한 문자열을 완전히 보존한다.
   - 하지만 앞뒤 공백과 공백-only 질문이 저장될 수 있다.

### 선택 이유

질문 문구는 사용자가 계속 보게 되는 핵심 데이터이고, LLM 입력의 문항 맥락으로도 사용된다. 불필요한 앞뒤 공백을 제거하면 화면 표시와 LLM 입력 품질이 안정된다. 원본 답변, 최종 작성본과 같은 trim 정책을 적용해 문자열 정규화 기준을 일관되게 유지한다.

### 트레이드오프

- 장점
  - 질문 문구와 답변의 문자열 정규화 정책이 일관된다.
  - 공백만 있는 질문 저장을 방지할 수 있다.
  - 화면 표시와 LLM 입력 데이터 품질이 좋아진다.

- 단점
  - 사용자가 의도적으로 질문 앞뒤에 공백을 넣어도 보존되지 않는다.
  - 원문 입력을 완전 그대로 보관하는 감사 요구가 생기면 별도 raw value 저장 정책이 필요하다.



## Decision 044: 자기소개서 문항 개수에는 제품 정책상 상한을 두지 않는다

### 결정

등록 step3의 DRAFT 임시저장에서는 문항이 없어도 되며, 제품 정책상 최대 개수 제한은 두지 않는다. API-014 제출 시에는 최소 1개 이상이어야 한다.

적용 API:

```http
PUT /cover-letters/{coverLetterId}/questions
```

Validation:

```text
DRAFT 저장 questions: 0개 이상, 제품 정책상 최대 개수 제한 없음
API-014 제출 questions: 1개 이상
```

단, 다음 인프라/운영 한계는 별도로 적용될 수 있다.

```text
HTTP request body size
DB 저장 한계
LLM provider context limit
LLM provider rate/usage limit
```

문항 수가 많아 LLM 입력 한계를 초과하면 첨삭 Job은 `FAILED`가 될 수 있다.

### PRD 근거

- PRD는 등록 step3에서 질문과 답변을 입력한다고 설명하지만, 문항 개수 상한을 명시하지 않는다.
- 사용자는 공고/회사 양식에 따라 여러 개의 자기소개서 문항을 입력할 수 있다.

### 고려한 대안

1. 1~5개
   - 일반 자기소개서 문항 수에 맞고 LLM 비용/응답 시간을 통제하기 쉽다.
   - 하지만 5개를 초과하는 회사 양식을 입력할 수 없다.

2. 1~10개
   - 더 많은 문항을 수용할 수 있다.
   - 하지만 여전히 특정 회사 양식이 10개를 넘으면 막힌다.

3. 상한 없음
   - 회사별 다양한 자기소개서 문항 수를 수용할 수 있다.
   - 대신 LLM 비용, 처리 시간, 실패 가능성이 커진다.

### 선택 이유

PRD가 문항 개수 상한을 요구하지 않고, 실제 자기소개서 문항 수는 회사별로 달라질 수 있다. 따라서 제품 정책으로 임의 상한을 두지 않는다. 다만 물리적으로 무한 처리는 불가능하므로 request size와 LLM context 같은 인프라 제한은 별도 운영 한계로 남긴다.

### 트레이드오프

- 장점
  - 회사별 다양한 자기소개서 양식을 유연하게 수용할 수 있다.
  - 사용자가 문항 수 때문에 입력을 포기하는 상황을 줄일 수 있다.
  - PRD에 없는 임의 제한을 API가 강제하지 않는다.

- 단점
  - 문항 수가 많을수록 LLM 비용과 응답 시간이 커진다.
  - LLM context limit을 초과하는 경우 Job 실패 가능성이 있다.
  - 화면 UX와 성능 측면에서 대량 문항 처리를 별도로 고려해야 한다.



## Decision 045: 문항 order는 서버가 요청 배열 순서대로 재부여한다

### 결정

등록 step3의 자기소개서 문항 순서는 클라이언트가 보낸 `questions` 배열 순서를 기준으로 한다.

서버는 요청 배열의 첫 번째 문항부터 `order=1`, `order=2`, `order=3`처럼 1부터 연속된 값을 재부여해 저장한다.

클라이언트는 요청에서 `order`를 보내지 않는다. 응답의 `order`는 서버가 부여한 저장 순서다.

적용 API:

```http
PUT /cover-letters/{coverLetterId}/questions
```

Request:

```json
{
  "questions": [
    {
      "question": "지원 동기를 작성해주세요.",
      "maxAnswerLength": 1000,
      "originalAnswer": "제가 지원한 이유는..."
    },
    {
      "question": "직무 관련 경험을 작성해주세요.",
      "maxAnswerLength": 1500,
      "originalAnswer": "저는 프로젝트에서..."
    }
  ]
}
```

저장 결과:

```text
첫 번째 문항 -> order=1
두 번째 문항 -> order=2
```

### PRD 근거

- 등록 step3은 사용자가 자기소개서 질문과 답변을 여러 개 입력하는 화면이다.
- AI 첨삭 결과와 최종 작성본은 문항 순서대로 보여줘야 한다.
- 사용자가 화면에서 정렬한 순서가 저장 순서가 되는 것이 가장 자연스럽다.

### 고려한 대안

1. 서버가 요청 배열 순서대로 `order`를 1부터 재부여
   - 클라이언트의 중복/누락 order 실수를 방지할 수 있다.
   - 드래그 정렬 UI와 잘 맞는다.

2. 클라이언트가 보낸 `order`를 엄격 검증
   - API 입력이 명시적이다.
   - 하지만 중복, 누락, 불연속 검증이 필요하고 프론트엔드 부담이 커진다.

3. `order` 필드를 제거하고 항상 배열 순서만 사용
   - 요청 모델은 단순하다.
   - 하지만 응답/저장 데이터에서 명시적인 순서 필드가 사라져 후속 기능에서 정렬 기준이 모호해질 수 있다.

### 선택 이유

요청에서는 배열 순서가 사용자의 의도와 가장 직접적으로 연결된다. 서버가 그 순서를 기준으로 연속된 `order`를 부여하면 저장 데이터는 명시적인 순서를 갖고, 클라이언트는 중복/누락 order를 관리하지 않아도 된다.

### 트레이드오프

- 장점
  - 클라이언트 구현이 단순해진다.
  - 서버 저장 데이터의 `order`가 항상 연속된다.
  - 문항 재정렬 시 배열 순서만 바꿔 보내면 된다.

- 단점
  - 클라이언트가 보낸 별도 `order` 값을 보존하는 방식은 지원하지 않는다.
  - 기존 문항 ID 기반 부분 수정이 아니라 전체 replace 성격이 강해진다.



## Decision 046: 문항 저장 API는 전체 replace 방식으로 동작한다

### 결정

등록 step3의 문항 저장 API는 부분 수정이 아니라 전체 replace 방식으로 동작한다.

요청의 `questions` 배열이 해당 자기소개서의 최종 문항 목록이 된다. 이전에 임시저장되어 DB에 존재하던 문항 중 요청 배열에 포함되지 않은 문항은 삭제된다.

적용 API:

```http
PUT /cover-letters/{coverLetterId}/questions
```

예시:

```text
기존 임시저장 문항: A, B, C
요청 questions: A, D
저장 후 문항: A, D
```

추가, 삭제, 재정렬은 모두 새 전체 `questions` 배열을 보내는 방식으로 처리한다.

### PRD 근거

- 등록 step3 화면에는 사용자가 현재 작성 중인 질문/답변 목록 전체가 있다.
- step3의 임시저장은 화면의 현재 전체 상태를 저장하는 흐름이다.
- 문항 순서는 Decision 045에 따라 요청 배열 순서로 서버가 재부여한다.

### 고려한 대안

1. 전체 replace
   - 요청한 `questions` 배열이 해당 자기소개서의 전체 문항 목록이 된다.
   - 삭제, 추가, 재정렬을 한 API로 처리할 수 있다.
   - 배열 순서 기반 order 재부여 정책과 잘 맞는다.

2. 부분 patch
   - 기존 문항 일부만 수정할 수 있다.
   - 하지만 추가, 삭제, 재정렬, order 재계산 규칙이 복잡해진다.

### 선택 이유

등록 step3은 화면 전체 상태를 저장하는 UX다. 사용자가 화면에서 문항을 추가/삭제/정렬한 뒤 임시저장하면, 서버는 그 화면 상태를 그대로 최종 저장 상태로 맞추는 것이 가장 단순하고 명확하다. 따라서 전체 replace 방식으로 정의한다.

### 트레이드오프

- 장점
  - API 의미가 명확하다.
  - 삭제, 추가, 재정렬을 별도 endpoint 없이 처리할 수 있다.
  - 서버가 연속된 order를 안정적으로 재부여할 수 있다.

- 단점
  - 한 문항만 바꿔도 전체 문항 payload를 보내야 한다.
  - 기존 문항 ID를 유지한 부분 수정 워크플로는 지원하지 않는다.
  - 동시 편집이 생기면 마지막 저장 요청이 전체 목록을 덮어쓴다.



## Decision 047: step1 기본 정보 저장은 PUT 전체 replace로 처리한다

### 결정

등록 step1의 기본 정보 저장 API는 `PUT`을 사용하며, 전체 replace 방식으로 동작한다.

요청 본문은 step1 기본 정보 전체를 포함해야 한다.

적용 API:

```http
PUT /cover-letters/{coverLetterId}/basic-info
```

Request:

```json
{
  "title": "2026 상반기 백엔드 개발자 자기소개서",
  "companyName": "Rewrite Corp",
  "positionTitle": "백엔드 개발자",
  "jobPostingUrl": "https://example.com/jobs/1"
}
```

Validation:

```text
coverLetter.status는 DRAFT여야 한다.
title: 필수, trim 후 Unicode code point 기준 1~50자
companyName: 필수, trim 후 Unicode code point 기준 1~30자
positionTitle: 필수, trim 후 Unicode code point 기준 1~30자
jobPostingUrl: 선택, trim 후 최대 500자, URL 형식
```

### PRD 근거

- 등록 step1은 자기소개서 제목, 회사명, 직무명, 지원 공고 링크를 한 화면에서 입력하는 흐름이다.
- PRD에는 필드별 저장이 아니라 step별 임시저장 버튼이 존재한다.
- step3 문항 저장도 화면 전체 상태를 저장하는 전체 replace 방식으로 결정했다.

### 고려한 대안

1. `PATCH` merge
   - 요청에 포함된 필드만 수정한다.
   - 자동 저장이나 필드별 수정에는 유리하지만, step1 화면 단위 저장 흐름과는 덜 맞는다.

2. `PUT` 전체 replace
   - step1 기본 정보 전체를 요청으로 보내고, 서버는 해당 값으로 기존 기본 정보를 교체한다.
   - 화면 단위 저장 의미가 명확하다.

### 선택 이유

step1은 필드별 편집 API라기보다 화면 전체 상태를 임시저장하는 흐름이다. 사용자가 step1 저장 버튼을 누르면 현재 화면의 기본 정보 전체가 저장되는 것이 자연스럽다. 따라서 `PUT /basic-info` 전체 replace 방식으로 정의한다.

### 트레이드오프

- 장점
  - API 의미가 명확하다.
  - step3의 `PUT /questions` 전체 replace 정책과 일관된다.
  - 누락 필드 검증과 저장 결과가 단순하다.

- 단점
  - 일부 필드만 바뀌어도 전체 기본 정보 payload를 보내야 한다.
  - 필드별 자동 저장을 도입하려면 별도 정책을 다시 검토해야 한다.



## Decision 048: step2 우대사항 저장은 PUT 전체 replace로 처리한다

### 결정

등록 step2의 채용 우대사항 저장 API는 `PUT`을 사용하며, 전체 replace 방식으로 동작한다.

요청의 `preferences` 값이 기존 우대사항 전체 텍스트를 대체한다.

적용 API:

```http
PUT /cover-letters/{coverLetterId}/preferences
```

Request:

```json
{
  "preferences": "Spring Boot 경험, 대용량 트래픽 처리 경험 우대"
}
```

Validation:

```text
coverLetter.status는 DRAFT여야 한다.
preferences: 필수, trim 후 Unicode code point 기준 1~3000자
```

### PRD 근거

- 등록 step2는 채용 우대사항을 한 화면에서 입력하는 흐름이다.
- PRD에는 필드별 저장이 아니라 step별 임시저장 버튼이 존재한다.
- step1 기본 정보와 step3 문항 저장은 화면 단위 전체 replace 방식으로 결정했다.

### 고려한 대안

1. `PUT` 전체 replace
   - step2 우대사항 전체 텍스트를 요청으로 보내고, 서버는 해당 값으로 기존 우대사항을 교체한다.
   - 화면 단위 저장 의미가 명확하다.

2. `PATCH` merge
   - 요청에 포함된 필드만 수정한다.
   - 하지만 step2는 사실상 `preferences` 하나라 merge의 실익이 작다.

### 선택 이유

step2는 우대사항 텍스트 전체를 작성하고 임시저장하는 화면이다. 일부 필드 수정 개념이 거의 없으므로 `PUT /preferences` 전체 replace 방식이 가장 단순하고, step1/step3의 화면 단위 저장 정책과도 일관된다.

### 트레이드오프

- 장점
  - API 의미가 명확하다.
  - step1, step3의 `PUT` 전체 replace 정책과 일관된다.
  - 저장 결과가 요청 본문과 동일해 추론하기 쉽다.

- 단점
  - 우대사항 일부만 바뀌어도 전체 텍스트를 보내야 한다.
  - 향후 우대사항을 구조화 필드로 나누면 저장 정책을 재검토해야 할 수 있다.



## Decision 049: 우대사항은 빈 문자열로 저장할 수 없다

> Superseded by Decision 096. DRAFT에서는 빈 값을 `null`로 임시저장하고 API-014 제출 시 우대사항을 필수 검증한다.

### 결정

등록 step2의 채용 우대사항 `preferences`는 필수이며, 빈 문자열을 허용하지 않는다.

서버는 `preferences`의 앞뒤 공백을 제거한 뒤 길이를 검증하고, trim된 값을 저장한다.

적용 API:

```http
PUT /cover-letters/{coverLetterId}/preferences
```

Validation:

```text
preferences: 필수, trim 후 Unicode code point 기준 1~3000자
```

`preferences`가 trim 후 빈 문자열이면 `VALIDATION_ERROR`를 반환한다.

### PRD 근거

- 등록 step2는 채용 우대사항을 입력하는 단계다.
- AI 첨삭은 우대사항 적합성, 직무 키워드, 회사/직무 맥락을 평가해야 한다.
- 제출 전 검증에서는 `preferences`가 저장되어 있어야 한다.

### 고려한 대안

1. 빈 문자열 불가, 1~3000자
   - AI 첨삭의 주요 입력인 우대사항을 보장할 수 있다.
   - 공백만 있는 입력을 방지할 수 있다.

2. 빈 문자열 허용, 0~3000자
   - 우대사항이 없는 공고도 저장할 수 있다.
   - 하지만 제출 전 필수 정보 검증이 느슨해지고, AI 첨삭 입력 맥락이 줄어든다.

### 선택 이유

Rewrite의 AI 첨삭은 자기소개서를 공고/직무 맥락에 맞게 개선하는 기능이다. 우대사항은 LLM이 직무 적합성을 판단하는 주요 입력이므로 빈 값으로 저장하지 않도록 제한한다.

### 트레이드오프

- 장점
  - AI 첨삭 입력의 최소 품질을 보장할 수 있다.
  - 공백만 있는 우대사항 저장을 방지할 수 있다.
  - 제출 전 필수 정보 검증이 명확하다.

- 단점
  - 우대사항이 명시되지 않은 공고라도 사용자가 내용을 입력해야 한다.
  - 향후 “우대사항 없음”을 명시적으로 허용하려면 별도 선택지나 정책 변경이 필요하다.



## Decision 050: step1 기본 정보 문자열은 앞뒤 공백을 trim한 뒤 검증하고 저장한다

> Superseded by Decision 096. 비어 있지 않은 값의 trim·최대 길이 정책은 유지하지만, DRAFT의 빈 값은 오류 대신 `null`로 임시저장하고 제출 시 필수 검증한다.

### 결정

등록 step1의 `title`, `companyName`, `positionTitle`은 서버에서 앞뒤 공백을 제거한 뒤 길이를 검증한다.

서버는 trim된 값을 저장한다.

적용 API:

```http
POST /cover-letters
PUT  /cover-letters/{coverLetterId}/basic-info
```

Validation:

```text
title: 필수, trim 후 Unicode code point 기준 1~50자
companyName: 필수, trim 후 Unicode code point 기준 1~30자
positionTitle: 필수, trim 후 Unicode code point 기준 1~30자
```

trim 후 빈 문자열이면 `VALIDATION_ERROR`를 반환한다.

### PRD 근거

- 등록 step1의 제목, 회사명, 직무명은 자기소개서 목록, 상세 화면, AI 첨삭 입력에 사용되는 핵심 데이터다.
- 공백만 있는 제목/회사명/직무명은 유효한 기본 정보로 보기 어렵다.
- 질문, 답변, 우대사항도 앞뒤 공백을 trim한 뒤 검증/저장하기로 결정했다.

### 고려한 대안

1. `title`, `companyName`, `positionTitle`도 trim 후 검증/저장
   - 질문, 답변, 우대사항 정책과 일관된다.
   - 공백만 있는 기본 정보 저장을 막을 수 있다.

2. 원문 그대로 저장
   - 사용자가 입력한 문자열을 완전히 보존한다.
   - 하지만 앞뒤 공백과 공백-only 값 처리 기준이 흔들린다.

### 선택 이유

기본 정보는 화면 표시와 LLM 입력 맥락에 모두 사용된다. 불필요한 앞뒤 공백을 저장하면 목록/상세 표시 품질이 떨어지고, 공백-only 값이 필수 검증을 통과할 수 있다. 따라서 다른 주요 문자열 입력과 동일하게 trim 후 검증/저장한다.

### 트레이드오프

- 장점
  - 기본 정보의 데이터 품질이 좋아진다.
  - 공백만 있는 필수값 저장을 방지할 수 있다.
  - 주요 문자열 입력의 정규화 정책이 일관된다.

- 단점
  - 사용자가 의도적으로 앞뒤 공백을 넣어도 보존되지 않는다.
  - 원문 입력을 완전 그대로 보관하는 감사 요구가 생기면 별도 raw value 저장 정책이 필요하다.



## Decision 051: 공고 링크는 앞뒤 공백을 trim한 뒤 URL 형식을 검증하고 저장한다

### 결정

선택 입력값인 `jobPostingUrl`도 서버에서 앞뒤 공백을 제거한 뒤 길이와 URL 형식을 검증한다.

서버는 trim된 값을 저장한다.

적용 API:

```http
POST /cover-letters
PUT  /cover-letters/{coverLetterId}/basic-info
```

Validation:

```text
jobPostingUrl: 선택, trim 후 최대 500자, URL 형식
```

`jobPostingUrl`이 비어 있거나 누락되면 `null`로 저장한다. 값이 있으면 trim 후 URL 형식이어야 한다.

### PRD 근거

- 등록 step1에서 사용자는 지원 공고 링크를 입력할 수 있다.
- 공고 링크는 화면 표시와 LLM 입력 맥락에 사용될 수 있는 참고 정보다.
- URL 앞뒤 공백은 의미 있는 값으로 보기 어렵다.

### 고려한 대안

1. 앞뒤 공백 trim 후 URL 형식 검증 및 저장
   - 사용자가 실수로 URL 앞뒤에 공백을 넣어도 정상 처리할 수 있다.
   - step1의 다른 문자열 정규화 정책과 일관된다.

2. 원문 그대로 저장
   - 사용자가 입력한 문자열을 완전히 보존한다.
   - 하지만 앞뒤 공백 때문에 URL 형식 검증이 실패하거나 저장값이 오염될 수 있다.

### 선택 이유

URL 앞뒤 공백은 사용자 의도라기보다 입력 실수에 가깝다. trim 후 검증하면 불필요한 실패를 줄이고, 저장값도 실제 URL 형태로 유지할 수 있다. Decision 035의 “URL 형식만 검증” 정책은 유지하되, 검증 전 정규화만 추가한다.

### 트레이드오프

- 장점
  - 공백이 섞인 URL 입력을 안정적으로 처리할 수 있다.
  - 저장된 URL 데이터 품질이 좋아진다.
  - step1 문자열 입력의 정규화 정책이 일관된다.

- 단점
  - 사용자가 의도적으로 URL 앞뒤에 공백을 넣어도 보존되지 않는다.
  - 원문 입력을 완전 그대로 보관하는 감사 요구가 생기면 별도 raw value 저장 정책이 필요하다.



## Decision 052: 빈 공고 링크는 null로 저장한다

### 결정

선택값인 `jobPostingUrl`이 누락되거나 trim 후 빈 문자열이면 `null`로 저장한다.

적용 API:

```http
POST /cover-letters
PUT  /cover-letters/{coverLetterId}/basic-info
```

정규화:

```text
jobPostingUrl omitted -> null
jobPostingUrl: null -> null
jobPostingUrl: "" -> null
jobPostingUrl: "   " -> null
jobPostingUrl: " https://example.com/jobs/1 " -> "https://example.com/jobs/1"
```

값이 `null`이 아니면 trim 후 최대 500자와 URL 형식을 검증한다.

### PRD 근거

- 등록 step1의 지원 공고 링크는 선택 입력값이다.
- 공고 링크가 없는 상태도 자기소개서 작성 흐름에서 허용되어야 한다.
- 빈 input은 사용자가 링크를 입력하지 않았다는 의미에 가깝다.

### 고려한 대안

1. 빈 문자열/trim 후 빈 문자열은 `null`로 저장
   - 선택 필드 의미와 맞다.
   - 프론트엔드가 빈 input을 그대로 보내도 서버가 안정적으로 정규화할 수 있다.

2. 빈 문자열이면 `VALIDATION_ERROR`
   - 입력 규칙은 엄격하다.
   - 하지만 선택 필드인데 빈 input 처리에 불필요하게 민감하다.

### 선택 이유

`jobPostingUrl`은 선택값이다. 선택값에서 빈 문자열은 유효하지 않은 URL이라기보다 “값 없음”에 가깝다. 따라서 빈 문자열을 에러로 처리하지 않고 `null`로 정규화한다.

### 트레이드오프

- 장점
  - 선택 필드의 값 없음 표현이 `null`로 통일된다.
  - 프론트엔드가 빈 input을 보내도 별도 분기 없이 처리할 수 있다.
  - 저장 데이터에서 빈 문자열과 값 없음이 섞이지 않는다.

- 단점
  - 사용자가 빈 문자열을 보냈다는 사실은 저장 데이터에 남지 않는다.
  - 향후 입력 원문 감사가 필요하면 별도 raw value 저장 정책이 필요하다.



## Decision 053: 제출 시 누락된 step 데이터는 VALIDATION_ERROR와 details로 반환한다

### 결정

자기소개서 제출 API 호출 시 필수 step 데이터가 누락되어 있으면 `VALIDATION_ERROR`를 반환한다.

응답의 `details`에는 누락된 `field`와 사용자 안내용 `reason`을 포함한다. 프론트엔드는 `field`를 등록 step과 매핑한다.

적용 API:

```http
POST /cover-letters/{coverLetterId}/submit
```

필수 데이터:

```text
STEP1: title, companyName, positionTitle
STEP2: preferences
STEP3: questions[].question, questions[].maxAnswerLength, questions[].originalAnswer
```

Response:

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "입력값이 올바르지 않습니다.",
    "details": [
      {
        "field": "preferences",
        "reason": "채용 우대사항을 입력해야 합니다."
      },
      {
        "field": "questions",
        "reason": "질문과 답변을 1개 이상 입력해야 합니다."
      }
    ]
  }
}
```

`jobPostingUrl`은 선택값이므로 제출 필수 데이터에 포함하지 않는다.

### PRD 근거

- 등록 완료 버튼을 누르면 AI 첨삭이 시작된다.
- AI 첨삭에는 회사명, 직무명, 우대사항, 질문/답변 같은 입력이 필요하다.
- step별 입력 화면이 있으므로 누락된 field를 프론트엔드가 해당 step과 연결할 수 있어야 한다.

### 고려한 대안

1. 누락 필드가 있으면 `VALIDATION_ERROR`와 missing field 목록 반환
   - 프론트엔드가 어느 step으로 이동시킬지 판단할 수 있다.
   - 사용자에게 정확한 안내를 제공할 수 있다.

2. 단순 `CONFLICT`만 반환
   - 구현은 단순하다.
   - 하지만 어떤 데이터가 부족한지 프론트엔드가 다시 조회해서 판단해야 한다.

### 선택 이유

제출은 AI 첨삭을 시작하기 직전의 최종 검증 단계다. 이 단계에서 누락된 정보를 구조적으로 내려주면 프론트엔드가 field를 기준으로 사용자를 정확한 step으로 돌려보내고, 어떤 값을 보완해야 하는지 바로 안내할 수 있다.

### 트레이드오프

- 장점
  - 사용자 안내가 정확해진다.
  - 프론트엔드가 누락 데이터 판단 로직을 중복 구현하지 않아도 된다.
  - 제출 실패 원인이 명확해진다.

- 단점
  - 서버가 누락 field와 사용자 안내 문구를 관리해야 한다.
  - 필수 입력 정책이 바뀌면 에러 details 정책도 함께 갱신해야 한다.



## Decision 054: 제출 중복 호출 시 기존 진행 중 Job을 반환한다

### 결정

자기소개서 제출 API가 중복 호출되었고, 이미 최초 첨삭 Job이 `PENDING` 또는 `PROCESSING` 상태이면 새 LLM Job을 만들지 않는다.

대신 기존 진행 중 Job의 `jobId`를 반환한다.

적용 API:

```http
POST /cover-letters/{coverLetterId}/submit
```

Response:

```json
{
  "coverLetterId": "cl_01HZ...",
  "status": "REVIEWING",
  "jobId": "job_existing_01HZ..."
}
```

### PRD 근거

- 등록 완료 버튼을 누르면 LLM이 첨삭을 시작하고 목록에서는 `첨삭 중`으로 표시된다.
- 사용자가 버튼을 중복 클릭하거나 네트워크 재시도로 같은 제출 요청이 다시 갈 수 있다.
- 첨삭 중인 동일 자기소개서에 대해 중복 첨삭 Job을 생성하면 비용과 상태 충돌이 발생한다.

### 고려한 대안

1. 이미 `REVIEWING`이면 기존 진행 중 Job 반환
   - 중복 Job 생성을 막을 수 있다.
   - 프론트엔드는 반환된 `jobId`로 기존 상태 조회 또는 SSE 재연결을 수행할 수 있다.

2. 이미 `REVIEWING`이면 `CONFLICT`
   - 엄격한 처리는 가능하다.
   - 하지만 프론트엔드가 기존 Job을 다시 조회해야 한다.

3. 항상 새 Job 생성
   - 구현은 단순해 보인다.
   - 하지만 중복 첨삭, 비용 증가, 최신 버전 충돌 위험이 크다.

### 선택 이유

제출 API는 버튼 중복 클릭과 네트워크 재시도에 노출되기 쉽다. 같은 자기소개서의 최초 첨삭은 하나만 실행되어야 하므로, 중복 호출은 멱등하게 기존 Job을 반환하는 것이 가장 안전하다.

### 트레이드오프

- 장점
  - 중복 LLM 비용을 막을 수 있다.
  - 프론트엔드가 기존 Job stream/status에 다시 붙기 쉽다.
  - 사용자 중복 클릭에도 상태가 안정적이다.

- 단점
  - 서버가 해당 자기소개서의 진행 중 최초 첨삭 Job을 조회해야 한다.
  - 사용자가 의도적으로 재시작하고 싶은 경우에는 별도 취소/재시도 정책이 필요하다.



## Decision 055: REVIEW_FAILED 상태에서는 submit 재호출로 최초 첨삭을 재시도할 수 있다

### 결정

최초 첨삭 Job이 실패해 `CoverLetter.status=REVIEW_FAILED`가 된 경우, 사용자는 submit API를 다시 호출해 최초 첨삭을 재시도할 수 있다.

재시도 시 새 최초 첨삭 Job을 생성하고 `CoverLetter.status`를 `REVIEWING`으로 전환한다.

적용 API:

```http
POST /cover-letters/{coverLetterId}/submit
```

상태 전이:

```text
REVIEW_FAILED
-> submit 재호출
-> 새 최초 첨삭 Job 생성
-> REVIEWING
-> 성공 시 REVIEWED
-> 실패 시 REVIEW_FAILED
```

### PRD 근거

- 최초 등록 완료 후 LLM이 첨삭하는 동안 목록에는 `첨삭 중`으로 표시된다.
- LLM 작업은 외부 provider나 네트워크 상태로 일시 실패할 수 있다.
- 최초 첨삭이 실패하면 사용자가 다시 시도할 수 있어야 한다.

### 고려한 대안

1. `REVIEW_FAILED` 상태에서 submit 재호출 허용
   - 최초 첨삭 실패 후 사용자가 복구할 수 있다.
   - 새 최초 첨삭 Job을 생성하고 성공 시 `REVIEWED`로 전환한다.

2. `REVIEW_FAILED`에서는 재제출 불가
   - 상태 모델은 단순하다.
   - 하지만 사용자가 실패 상태에서 벗어날 방법이 없다.

### 선택 이유

LLM 실패는 일시 장애일 수 있다. 최초 첨삭 실패 후 복구 경로가 없으면 사용자는 자기소개서를 다시 만들어야 할 수 있다. 따라서 `REVIEW_FAILED` 상태에서는 submit 재호출로 최초 첨삭을 재시도할 수 있게 한다.

### 트레이드오프

- 장점
  - 사용자가 일시적 LLM 실패에서 복구할 수 있다.
  - 실패한 자기소개서를 새로 만들 필요가 없다.
  - `REVIEW_FAILED` 상태의 의미가 “재시도 가능”으로 명확해진다.

- 단점
  - 실패한 이전 Job과 새 재시도 Job을 구분해 추적해야 한다.
  - 반복 실패 시 사용자 안내와 재시도 제한 정책이 추가로 필요할 수 있다.



## Decision 056: REVIEWED 상태에서 submit 재호출 시 기존 최신 첨삭 결과 정보를 반환한다

### 결정

이미 최초 첨삭이 완료되어 `CoverLetter.status=REVIEWED`인 자기소개서에 대해 submit API가 다시 호출되면 새 LLM Job을 만들지 않는다.

대신 기존 최신 `ReviewVersion` 정보를 반환한다.

적용 API:

```http
POST /cover-letters/{coverLetterId}/submit
```

Response:

```json
{
  "coverLetterId": "cl_01HZ...",
  "status": "REVIEWED",
  "jobId": null,
  "latestReviewVersionId": "rv_01HZ..."
}
```

### PRD 근거

- 등록 완료 버튼은 최초 AI 첨삭을 시작하기 위한 동작이다.
- 최초 첨삭이 이미 완료된 자기소개서는 결과 화면을 보여주는 흐름이 자연스럽다.
- 같은 자기소개서에 대해 submit을 다시 호출했다고 해서 최초 첨삭 Job을 새로 만들면 비용과 버전 충돌이 발생한다.

### 고려한 대안

1. `REVIEWED` 상태에서는 기존 최신 `ReviewVersion` 정보 반환
   - submit API를 멱등적으로 다룰 수 있다.
   - 프론트엔드는 응답을 보고 바로 결과 화면으로 이동할 수 있다.
   - 새 LLM Job을 만들지 않아 비용과 버전 충돌을 막을 수 있다.

2. `REVIEWED` 상태에서는 `CONFLICT` 반환
   - 상태 규칙은 엄격해진다.
   - 하지만 프론트엔드가 다시 상세 조회를 호출해야 하므로 사용자 흐름이 불필요하게 복잡해진다.

3. `REVIEWED` 상태에서도 새 첨삭 Job 생성
   - 사용자가 다시 첨삭받는 동작처럼 보일 수 있다.
   - 하지만 최초 첨삭 submit의 의미가 흐려지고, 재첨삭 API와 책임이 겹친다.

### 선택 이유

submit API는 최초 첨삭 시작 요청이지만, 네트워크 재시도나 화면 재진입으로 완료 후 다시 호출될 수 있다. 이미 결과가 있는 경우에는 기존 최신 결과를 반환하는 것이 프론트엔드 흐름과 비용 측면에서 가장 안정적이다.

재첨삭은 별도 재첨삭 API에서 다루며, submit API가 새 첨삭 버전을 생성하지 않는다.

### 트레이드오프

- 장점
  - 완료된 submit 요청을 멱등적으로 처리할 수 있다.
  - 프론트엔드가 추가 조회 없이 결과 화면으로 이동할 수 있다.
  - 중복 LLM 비용과 불필요한 ReviewVersion 생성을 막을 수 있다.

- 단점
  - `REVIEWED` 상태인데 `latestReviewVersionId`가 없는 데이터 불일치 상황을 서버가 별도로 감지해야 한다.
  - 사용자가 의도적으로 다시 첨삭받고 싶은 경우에는 submit이 아니라 재첨삭 API를 사용해야 한다.



## Decision 057: REVIEW_FAILED 상태에서도 원본 수정 API는 허용하지 않는다

### 결정

`CoverLetter.status=REVIEW_FAILED` 상태에서도 등록 step1~step3의 원본 수정 API는 사용할 수 없다.

즉, `basic-info`, `preferences`, `questions` 저장 API는 계속 `DRAFT` 상태에서만 허용한다.

적용 API:

```http
PUT /cover-letters/{coverLetterId}/basic-info
PUT /cover-letters/{coverLetterId}/preferences
PUT /cover-letters/{coverLetterId}/questions
```

`REVIEW_FAILED` 상태에서 최초 첨삭을 재시도할 때는 기존에 저장된 원본 입력값으로 submit API를 다시 호출한다.

```http
POST /cover-letters/{coverLetterId}/submit
```

### PRD 근거

- 등록 step4는 작성 내용을 확인하고 완료하는 단계이며, 완료 후 AI 첨삭이 시작된다.
- 기존 결정에서 제출 후 원본 자기소개서 정보, 우대사항, 질문, 원본 답변은 수정하지 않는 것으로 정했다.
- `REVIEW_FAILED` 재시도는 LLM 작업 실패 복구 경로이며, 원본 편집 재개를 의미하지 않는다.

### 고려한 대안

1. `REVIEW_FAILED` 상태에서도 원본 수정 불가
   - 제출 후 원본 잠금 정책을 유지할 수 있다.
   - 실패 재시도는 저장된 동일 입력으로만 수행된다.
   - 상태별 편집 가능 범위가 단순하다.

2. `REVIEW_FAILED` 상태에서는 원본 수정 허용
   - 사용자가 실패 후 오타나 답변을 고칠 수 있다.
   - 하지만 제출 후 원본 잠금 정책에 예외가 생기고, 실패 원인이 LLM 장애인지 입력 문제인지에 따라 UX가 복잡해진다.

### 선택 이유

`REVIEW_FAILED`는 최초 첨삭 Job의 실패 상태이지, 작성 플로우가 다시 `DRAFT`로 돌아간 상태가 아니다. 따라서 재시도는 허용하되 원본 편집은 계속 막아 제출 후 원본 잠금 정책을 유지한다.

원본을 수정하고 다시 첨삭받는 흐름이 필요해지면, 기존 자기소개서를 복제해 새 `DRAFT`로 편집하는 별도 기능으로 다루는 편이 상태 모델이 명확하다.

### 트레이드오프

- 장점
  - `DRAFT`에서만 원본 수정 가능하다는 규칙이 유지된다.
  - 실패 재시도와 원본 편집 재개를 분리할 수 있다.
  - 기존 첨삭/버전/최종 작성본 모델과 충돌하지 않는다.

- 단점
  - 사용자가 실패 후 입력 내용을 고치고 싶으면 바로 수정할 수 없다.
  - 입력 내용 자체가 LLM 실패를 유발한 경우, 단순 재시도로는 복구되지 않을 수 있다.
  - 향후에는 `복제해서 새 자기소개서로 편집` 같은 별도 기능이 필요할 수 있다.



## Decision 058: REVIEW_FAILED 상태의 사용자 수동 재시도에는 제품 도메인상 횟수 제한을 두지 않는다

### 결정

`CoverLetter.status=REVIEW_FAILED` 상태에서 사용자가 submit API를 다시 호출하는 수동 재시도에는 제품 도메인상 횟수 제한을 두지 않는다.

적용 API:

```http
POST /cover-letters/{coverLetterId}/submit
```

이 결정은 LLM Job 내부 자동 재시도 정책과 별개다. LLM Job은 실패 시 서버에서 1회 자동 재시도하고, 그 후에도 실패하면 `FAILED`가 된다. 이후 사용자가 `REVIEW_FAILED` 상태에서 submit을 다시 호출하는 수동 재시도는 별도 횟수 제한 없이 허용한다.

단, LLM 비용과 남용 방지를 위한 rate limit, 사용자 quota, 운영 정책은 별도로 적용할 수 있다.

### PRD 근거

- 최초 첨삭 실패 후 사용자는 다시 시도할 수 있어야 한다.
- LLM 실패는 외부 provider, 네트워크, 일시 장애 같은 비즈니스 도메인 밖의 원인으로 발생할 수 있다.
- PRD는 사용자별 첨삭 재시도 횟수나 과금 제한을 명시하지 않는다.

### 고려한 대안

1. 제품 정책상 수동 재시도 횟수 제한 없음
   - 일시 장애가 길어져도 사용자가 계속 복구를 시도할 수 있다.
   - API 도메인 모델이 단순하다.
   - 비용/남용 통제는 rate limit, quota, 운영 정책으로 분리한다.

2. 자기소개서별 최초 첨삭 수동 재시도 최대 N회
   - 비용 통제가 쉽다.
   - 하지만 N 값을 정해야 하고, 외부 장애가 길게 이어진 경우 정상 사용자도 막힐 수 있다.

### 선택 이유

최초 첨삭 실패는 사용자의 잘못보다 외부 LLM 또는 네트워크 실패일 가능성이 있다. 따라서 자기소개서 도메인 규칙으로 재시도 횟수를 제한하기보다는, submit 재시도는 열어두고 비용과 남용은 별도의 rate limit 또는 사용량 정책에서 통제하는 편이 실무적으로 더 유연하다.

### 트레이드오프

- 장점
  - 사용자가 일시적 실패에서 계속 복구할 수 있다.
  - API 상태 모델이 단순하다.
  - 도메인 정책과 운영/과금 정책의 책임이 분리된다.

- 단점
  - 별도 rate limit이나 quota가 없으면 반복 호출로 LLM 비용이 증가할 수 있다.
  - 같은 입력이 계속 실패하는 경우 사용자에게 더 구체적인 실패 안내가 필요할 수 있다.
  - 운영 정책이 정해지기 전까지는 남용 방어가 약할 수 있다.



## Decision 059: REVIEW_FAILED 항목 클릭 시 AI 첨삭 실패 화면으로 이동한다

### 결정

내 자기소개서 목록에서 `CoverLetter.status=REVIEW_FAILED`인 항목을 클릭하면 프론트엔드는 AI 첨삭 실패 화면으로 이동한다.

목록 카드 클릭 라우팅:

```text
DRAFT: 등록 step 화면
REVIEWING: AI 첨삭 진행 화면
REVIEWED: AI 첨삭 결과 화면
REVIEW_FAILED: AI 첨삭 실패 화면
```

`REVIEW_FAILED` 실패 화면에서는 저장된 원본 입력값을 표시할 수 있지만, 원본 수정은 제공하지 않는다. 사용자는 이 화면에서 submit 재시도를 실행할 수 있다.

### PRD 근거

- 등록 완료 후 LLM 첨삭이 시작되고, 목록에는 첨삭 진행/완료 상태가 표시된다.
- 최초 첨삭 실패는 작성 중 상태가 아니라 첨삭 작업 실패 상태다.
- 기존 결정에서 `REVIEW_FAILED` 상태의 원본 수정은 막고, submit 재시도만 허용하기로 했다.

### 고려한 대안

1. AI 첨삭 실패 화면으로 이동
   - 실패 상태와 재시도 동작을 한 화면에서 명확히 보여줄 수 있다.
   - 원본 수정 불가 정책과 일관된다.
   - 작성 플로우와 첨삭 플로우를 분리할 수 있다.

2. 등록 step4 확인 화면으로 이동
   - 사용자가 제출했던 내용을 다시 확인하기 쉽다.
   - 하지만 수정 불가 확인 화면이 작성 단계처럼 보일 수 있어 혼동이 생긴다.

3. 목록에서만 재시도 제공
   - 화면 전환은 줄어든다.
   - 하지만 실패 원인, 저장된 입력 확인, 재시도 안내를 충분히 보여주기 어렵다.

### 선택 이유

`REVIEW_FAILED`는 사용자가 작성 중인 상태가 아니라 최초 첨삭 Job이 실패한 상태다. 따라서 목록 클릭 시 등록 step으로 보내기보다 AI 첨삭 페이지 계열의 실패 화면으로 보내는 것이 상태 모델과 사용자 안내 측면에서 명확하다.

### 트레이드오프

- 장점
  - 실패 상태, 재시도 버튼, 원본 수정 불가 정책을 한 화면에서 일관되게 표현할 수 있다.
  - 작성 플로우와 첨삭 플로우가 섞이지 않는다.
  - 향후 실패 사유, Job 상태, 재시도 안내를 확장하기 쉽다.

- 단점
  - 별도의 첨삭 실패 화면 또는 상태 뷰가 필요하다.
  - 사용자가 단순히 제출 내용을 확인하고 싶은 경우에도 첨삭 실패 화면을 거쳐야 한다.



## Decision 060: 자기소개서 상세 응답에 최근 최초 첨삭 Job 요약을 포함한다

> Superseded by Decision 074. 상세 응답은 최초 첨삭 Job 전용 요약 대신 공통 `reviewJob`과 문항 결과 구조를 사용한다.

### 결정

자기소개서 상세 조회 응답에 최근 최초 첨삭 Job 요약인 `latestFirstReviewJob`을 포함한다.

적용 API:

```http
GET /cover-letters/{coverLetterId}
```

응답 필드:

```json
{
  "latestFirstReviewJob": {
    "jobId": "job_01HZ...",
    "status": "FAILED",
    "progress": {
      "current": 0,
      "total": 3,
      "message": "LLM 첨삭에 실패했습니다."
    },
    "error": {
      "code": "LLM_PROVIDER_ERROR",
      "message": "LLM 응답 생성에 실패했습니다."
    },
    "createdAt": "2026-06-20T14:10:00",
    "completedAt": "2026-06-20T14:12:00"
  }
}
```

`latestFirstReviewJob`은 최초 첨삭 Job(`type=COVER_LETTER_REVIEW`) 중 가장 최근 Job의 요약이다.

상태별 의미:

```text
DRAFT: null
REVIEWING: 진행 중인 최초 첨삭 Job 요약
REVIEW_FAILED: 실패한 최근 최초 첨삭 Job 요약
REVIEWED: latestReviewVersionId를 기준으로 결과를 조회하므로 null 허용
```

### PRD 근거

- 목록에서 첨삭 중/첨삭 완료/첨삭 실패 상태를 보여줘야 한다.
- `REVIEW_FAILED` 항목 클릭 시 AI 첨삭 실패 화면으로 이동하기로 했다.
- 실패 화면은 실패 사유와 재시도 동작을 보여줄 수 있어야 한다.
- 진행 중 화면은 새로고침 또는 재진입 시 기존 Job 상태를 복구할 수 있어야 한다.

### 고려한 대안

1. 자기소개서 상세 응답에 최근 최초 첨삭 Job 요약 포함
   - 실패 화면과 진행 화면 복구에 필요한 정보를 한 번의 상세 조회로 얻을 수 있다.
   - 목록 응답은 가볍게 유지할 수 있다.
   - 별도 API를 추가하지 않아도 된다.

2. 별도 API 추가
   - 예: `GET /cover-letters/{coverLetterId}/latest-first-review-job`
   - 리소스 책임은 명확하다.
   - 하지만 실패 화면 진입 시 상세 조회와 Job 조회를 따로 호출해야 하거나 API가 늘어난다.

3. 실패 화면은 구체적인 Job 정보 없이 일반 실패 메시지만 표시
   - 구현은 가장 단순하다.
   - 하지만 실패 원인 안내와 운영 디버깅에 불리하다.

4. 목록 응답에 최근 최초 첨삭 Job 요약 포함
   - 목록에서 바로 실패 사유를 표시할 수 있다.
   - 하지만 목록 API가 무거워지고, 목록 카드에 필요하지 않은 상세 Job 정보까지 매번 내려가게 된다.

### 선택 이유

`REVIEW_FAILED` 실패 화면과 `REVIEWING` 진행 화면은 자기소개서 상세 진입 후 화면을 복구해야 한다. 이때 최근 최초 첨삭 Job 요약을 상세 응답에 포함하면 프론트엔드는 추가 API 없이 필요한 상태, 진행 메시지, 실패 사유를 얻을 수 있다.

반면 목록 화면은 카드 표시와 라우팅에 `status`만 있으면 충분하므로, Job 상세 정보를 목록 응답에 포함하지 않는다.

### 트레이드오프

- 장점
  - 실패 화면에서 구체적인 실패 메시지를 보여줄 수 있다.
  - 진행 중 화면 재진입 시 기존 Job에 다시 연결하기 쉽다.
  - 목록 API를 가볍게 유지할 수 있다.
  - 별도 최신 Job 조회 API를 만들지 않아도 된다.

- 단점
  - 자기소개서 상세 조회가 최근 최초 첨삭 Job을 함께 조회해야 한다.
  - 상세 응답이 순수 자기소개서 데이터뿐 아니라 화면 복구용 Job 요약도 포함하게 된다.
  - `REVIEWED` 상태에서는 `latestReviewVersionId`와 `latestFirstReviewJob` 중 어떤 필드를 우선할지 프론트 규칙이 필요하다.



## Decision 070: 삭제된 자기소개서와 하위 리소스는 사용자-facing API에서 모두 NOT_FOUND로 응답한다

### 결정

`CoverLetter.deletedAt`이 있는 삭제된 자기소개서와 그 하위 리소스는 사용자-facing API에서 모두 `NOT_FOUND`를 반환한다.

적용 대상:

```text
CoverLetter
CoverLetterQuestion
ReviewVersion
ReviewVersionQuestionResult
KeywordAnalysis
InterviewSession
InterviewQuestion
InterviewThread
InterviewMessage
LlmJob
```

예:

```text
GET /cover-letters/{coverLetterId}
GET /cover-letters/{coverLetterId}/review-versions
GET /cover-letters/{coverLetterId}/keyword-analysis/latest
GET /cover-letters/{coverLetterId}/interview
GET /interview-threads/{threadId}/messages
GET /llm-jobs/{jobId}
```

삭제된 자기소개서에 연결된 위 API는 모두 `NOT_FOUND`를 반환한다.

### PRD 근거

- 자기소개서는 soft delete로 처리하기로 했다.
- MVP에서는 삭제된 자기소개서 목록 조회 API와 사용자-facing 복구 API를 제공하지 않기로 했다.
- 사용자 화면에서 삭제된 자기소개서는 더 이상 접근 가능한 문서로 보이지 않아야 한다.

### 고려한 대안

1. 삭제된 자기소개서와 하위 리소스 모두 `NOT_FOUND`
   - 삭제 후 사용자-facing API 동작이 일관된다.
   - 삭제된 문서의 일부 결과만 열리는 혼란을 막을 수 있다.
   - 복구 API가 없는 MVP 정책과 맞다.

2. 삭제된 자기소개서 상세만 `NOT_FOUND`, 하위 결과는 읽기 허용
   - 사용자가 과거 첨삭 결과나 면접 기록 일부를 볼 수 있다.
   - 하지만 삭제한 자기소개서의 데이터가 일부 화면에서 계속 열려 UX가 불명확하다.

3. 삭제된 리소스는 `GONE` 또는 별도 에러 코드 반환
   - 삭제되었다는 상태를 명확히 알릴 수 있다.
   - 하지만 사용자-facing 복구 기능이 없고, 삭제된 리소스 존재 여부를 더 드러낸다.

### 선택 이유

MVP에서 삭제는 사용자 화면에서 해당 자기소개서를 제거하는 동작이다. 삭제된 자기소개서의 첨삭 결과, 키워드 분석, 면접 데이터가 계속 접근 가능하면 사용자는 삭제의 의미를 혼동할 수 있다. 따라서 삭제된 자기소개서와 모든 하위 리소스는 사용자-facing API에서 존재하지 않는 것처럼 `NOT_FOUND`로 응답한다.

### 트레이드오프

- 장점
  - 삭제 후 사용자 경험이 명확하다.
  - 목록/상세/하위 리소스 접근 정책이 일관된다.
  - 삭제된 리소스 존재 여부 노출을 줄일 수 있다.

- 단점
  - 사용자는 삭제 후 첨삭 결과나 면접 기록도 다시 볼 수 없다.
  - 운영자 복구나 감사 조회는 별도 내부 도구나 DB 대응에 의존해야 한다.
  - 향후 사용자-facing 복구 기능을 만들면 접근 정책을 재검토해야 한다.

## Decision 074: 자기소개서 상세와 첨삭 버전 상세는 같은 응답 구조를 사용한다

### 결정

API-012 자기소개서 상세와 API-018 첨삭 버전 상세는 `coverLetter`, `reviewVersion`, `reviewJob`, `questions`로 구성된 같은 최상위 응답 구조를 사용한다. `coverLetter`는 내부 상태 대신 API-007과 같은 `displayStatus`를 반환한다.

API-012는 `WRITING`, `REVIEWING`, `REVIEW_FAILED`, `REVIEWED` 모든 표시 상태에서 사용한다. `reviewVersion`은 최신 성공 버전이 없으면 `null`이며, `reviewJob`은 진행 중이거나 가장 최근 실패한 첨삭 Job 요약이다. `REVIEWED`이면 최신 `ReviewVersion` 전체 결과를 직접 반환하고, API-018은 사용자가 히스토리에서 선택한 특정 버전을 조회할 때만 사용한다. API-018의 `reviewJob`은 항상 `null`이다.

### 선택 이유

현재 상세 화면과 버전 상세 화면은 같은 UI를 사용한다. 서로 다른 응답 모델을 사용하면 프론트엔드가 같은 컴포넌트에 상태별 변환 계층을 추가해야 하므로, 화면이 필요로 하는 모델을 하나로 고정한다.

### 트레이드오프

- 장점: 상태와 버전에 관계없이 같은 UI 모델을 재사용할 수 있고 `REVIEWED` 진입 시 추가 요청이 필요 없다.
- 단점: API-012가 자기소개서, Job, 버전 결과를 함께 조합해야 하므로 조회 책임과 쿼리가 커진다.

## Decision 077: 메인 첨삭 상태는 사용자 단일 SSE 연결로 갱신한다

### 결정

API-007 목록 항목과 query filter는 내부 자기소개서·Job 상태 대신 메인 화면 표시용 `displayStatus=WRITING|REVIEWING|REVIEWED|REVIEW_FAILED`를 사용한다. 현재 최초 첨삭 또는 재첨삭 Job이 `PENDING`이나 `PROCESSING`이면 `displayStatus=REVIEWING`으로 계산한다. 최초·재첨삭의 최신 시도가 실패하면 `displayStatus=REVIEW_FAILED`로 계산한다. 메인 화면은 카드마다 연결하지 않고 API-030 `GET /cover-letters/stream` 연결 하나로 현재 사용자의 첨삭 상태 변경을 수신한다.

연결 직후 soft delete되지 않은 모든 자기소개서의 현재 표시 상태를 `cover-letter.review-status.snapshot` 이벤트의 `items` 배열로 한 번에 전송한다. 이후 상태가 바뀐 자기소개서는 `cover-letter.review-status.changed` 단건 이벤트로 전송한다. 이벤트 이름으로 스냅샷과 변경을 구분하므로 `eventPhase`와 `changeType`은 사용하지 않는다. `PENDING → PROCESSING`은 표시 상태를 바꾸지 않으므로 메인 스트림에 노출하지 않는다.

프론트엔드는 모든 이벤트에서 `displayStatus`와 `latestReviewVersionId`를 목록 항목에 그대로 함께 반영하고 내부 상태를 조합하지 않는다. 최초·재첨삭 실패는 모두 `displayStatus=REVIEW_FAILED`다. 최초 첨삭 실패는 `latestReviewVersionId=null`, 재첨삭 실패는 기존 성공 버전 ID를 유지한다. 서버는 연결을 이벤트 라우터에 등록한 뒤 스냅샷을 조회·전송하며, 그 사이 발생한 변경 이벤트를 연결별로 버퍼링해 스냅샷 다음에 발생 순서대로 전송한다.

### 선택 이유

목록 카드 수에 비례해 SSE 연결을 만들 필요가 없고, 서버가 메인 화면 상태를 계산하므로 프론트엔드가 서로 다른 두 상태 모델을 조합하지 않아도 된다. 전체 현재 상태 스냅샷은 목록 조회와 스트림 연결 사이에 종료된 Job으로 인한 stale 상태를 해소한다. 이벤트 이름과 `displayStatus`만으로 처리 경로를 결정하며, `latestReviewVersionId`로 실패 화면에서 이전 성공 결과 접근 가능 여부를 구분한다.

### 트레이드오프

- 장점: 연결 수가 사용자당 하나로 고정되고 목록 상태가 실시간으로 갱신된다. 프론트엔드는 이벤트 이름과 표시 상태를 그대로 사용하며, 연결 시점의 상태 변경 누락도 복구한다.
- 단점: 서버가 화면 표시 상태 계산, 사용자별 이벤트 라우팅, 전체 현재 상태 스냅샷 조회와 스냅샷 전송 중 변경 이벤트 버퍼링을 지원해야 한다. 스냅샷 크기는 자기소개서 수에 비례해 증가한다.

## Decision 080: 자기소개서 생성 응답은 id만 반환한다

### 결정

API-008 자기소개서 생성 성공 응답은 생성된 자기소개서의 `id`만 반환한다. 생성 직후 항상 같은 내부 `status=DRAFT`와 등록 화면에서 사용하지 않는 `createdAt`은 공개 응답에서 제외한다.

### 선택 이유

프론트엔드는 생성 성공 후 `id`로 등록 1단계 화면을 여는 것만 필요하다. 사용하지 않는 내부 상태와 생성 시각을 노출하지 않으면 응답 계약과 프론트엔드 의존 범위를 작게 유지할 수 있다.

### 트레이드오프

- 장점: 생성 흐름에 필요한 값만 반환하고 내부 상태 모델 노출을 줄인다.
- 단점: 생성 직후 목록 항목을 낙관적으로 추가하려면 API-007 목록을 다시 조회해야 한다.

## Decision 081: 등록 단계 저장 응답은 성공 여부만 반환한다

### 결정

API-009 기본 정보 저장, API-010 우대사항 저장, API-011 질문과 답변 저장의 성공 응답은 `success=true`만 반환한다. 저장된 입력값, 자기소개서와 문항 ID, 서버 부여 순서, 내부 상태와 수정 시각은 응답하지 않는다.

### 선택 이유

프론트엔드는 임시저장 요청에 사용한 현재 폼 값을 이미 가지고 있고, 성공 후 저장 완료 표시 또는 다음 등록 단계 이동을 자체적으로 결정한다. 이후 흐름에 사용하지 않는 저장값을 다시 반환하지 않으면 응답 계약과 내부 모델 의존 범위를 줄일 수 있다.

### 트레이드오프

- 장점: 프론트엔드가 성공 여부만 처리하면 되고 내부 상태가 노출되지 않는다.
- 단점: 서버가 trim하거나 `null`로 정규화한 값을 즉시 확인하려면 별도 상세 조회가 필요하다.

## Decision 083: 자기소개서 삭제 응답은 성공 여부만 반환한다

### 결정

API-013 자기소개서 삭제 성공 응답은 `success=true`만 반환한다. 내부 soft delete 시각과 함께 취소한 Job 정보는 응답하지 않는다.

### 선택 이유

프론트엔드는 삭제 성공 후 목록에서 항목을 제거하며 내부 삭제 시각을 사용하지 않는다. 화면 동작에 필요한 성공 여부만 반환해 persistence 세부사항 노출을 줄인다.

### 트레이드오프

- 장점: 삭제 응답이 단순하고 내부 soft delete 구현과 분리된다.
- 단점: 삭제 시각이 필요한 관리 기능은 별도 API가 필요하다.

## Decision 084: 최초 첨삭 제출 응답은 표시 상태와 Job ID만 반환한다

### 결정

API-014 최초 첨삭 제출 성공 응답은 `displayStatus`와 nullable `jobId`만 반환한다. 새 Job을 생성하거나 기존 진행 중 Job을 반환하면 `displayStatus=REVIEWING`과 Job ID를 반환하고, 이미 첨삭이 완료되었으면 `displayStatus=REVIEWED`, `jobId=null`을 반환한다. 요청 본문은 사용하지 않는다.

### 선택 이유

자기소개서 ID는 path와 중복되고 최신 결과는 API-012에서 조회하므로 최신 버전 ID를 응답할 필요가 없다. 프론트엔드는 표시 상태로 이동 화면을 정하고 진행 중일 때만 Job ID로 API-016에 연결하면 된다.

### 트레이드오프

- 장점: 응답이 화면 분기와 SSE 연결에 필요한 값만 포함하고 공개 상태 이름을 통일한다.
- 단점: 이미 완료된 최신 버전 ID가 필요하면 API-012를 조회해야 한다.

## Decision 096: 등록 단계 API는 미완성 DRAFT를 임시저장하고 제출 시 필수값을 검증한다

### 결정

API-009~011은 별도의 임시저장 API를 추가하지 않고 각 등록 step의 현재 폼 전체를 DRAFT 스냅샷으로 저장한다. 요청 필드의 누락·`null`·trim 후 빈 문자열은 미입력값인 `null`로 정규화한다. 값이 있으면 최대 길이, 숫자 범위와 URL 형식을 저장 시 검증하지만 필수값 여부는 강제하지 않는다.

API-011의 `questions`가 누락·`null`·빈 배열이면 문항을 모두 삭제하며, 배열 내부 문항 필드도 DRAFT에서는 nullable이다. 이를 위해 원본 문항 persistence의 `question`, `maxAnswerLength`, `originalAnswer`는 nullable을 허용한다.

API-012는 `WRITING` 상태에서 미완성 기본 정보와 nullable 원본 문항을 그대로 반환한다. API-014만 모든 등록 필드와 문항의 필수값 완성 여부를 검증하며, 누락이 있으면 필드별 `VALIDATION_ERROR`를 반환하고 첨삭 Job을 생성하지 않는다.

### 선택 이유

현재 step 저장 API와 별도의 임시저장 API를 함께 두면 같은 데이터를 저장하는 endpoint, DTO와 service 로직이 중복된다. 단계 완료 여부를 서버가 별도 상태로 관리하지 않는 현재 모델에서는 기존 step API가 DRAFT 스냅샷을 저장하고 제출 API가 최종 완성도를 검증하는 구조가 더 단순하다.

### 트레이드오프

- 장점
  - 임시저장 API 3개를 추가하지 않고 기존 endpoint를 재사용한다.
  - 사용자는 필드를 모두 채우기 전에 이탈해도 입력 상태를 복구할 수 있다.
  - 필수값 검증 경계가 제출 API 하나로 명확해진다.
- 단점
  - 원본 문항 테이블의 일부 컬럼을 nullable로 변경해야 한다.
  - step 저장 성공이 해당 단계의 작성 완료를 의미하지 않으므로 다음 단계 이동 가능 여부는 프론트엔드가 판단해야 한다.
  - 전체 replace 자동 저장 요청의 도착 순서가 뒤바뀌면 이전 스냅샷이 최신 입력을 덮을 수 있어 프론트엔드는 요청을 직렬화해야 한다.
