# Review Version API Decisions

## Decision 002: 버전 히스토리는 AI 첨삭 결과를 기준으로 관리한다

### 결정

자기소개서의 버전 히스토리는 AI 첨삭 또는 재첨삭 결과를 기준으로 생성한다.

사용자가 `AI첨삭 다시받기`를 실행하고 LLM 첨삭이 완료되면 새로운 `ReviewVersion`이 생성된다. 사용자가 `최종 작성본`을 편집하고 저장하는 행위만으로는 새 버전이 생성되지 않는다.

리소스 분리:

```text
CoverLetter
CoverLetterQuestion
ReviewVersion
ReviewVersionQuestionResult
```

API 형태:

```http
GET  /cover-letters/{coverLetterId}/review-versions
GET  /cover-letters/{coverLetterId}/review-versions/{versionId}
POST /cover-letters/{coverLetterId}/review-versions
PUT  /cover-letters/{coverLetterId}/review-versions/{versionId}/final-answers
```

### PRD 근거

- `AI첨삭 다시받기` 버튼을 누르면 첨삭 요구사항을 작성하고 새 첨삭이 시작된다.
- 새로 첨삭된 자기소개서는 새로운 버전으로 생성되어 저장된다.
- 버전 히스토리는 `v0.1` 같은 버전 표시와 기록 시각을 보여준다.

### 고려한 대안

1. AI 첨삭 결과 버전
   - 재첨삭할 때마다 새 `ReviewVersion`을 생성한다.
   - 각 버전은 AI 리포트와 AI 수정본을 가진다.
   - 사용자의 `최종 작성본`은 별도 저장값으로 관리한다.

2. 최종 작성본까지 포함한 전체 작업 버전
   - 재첨삭뿐 아니라 사용자가 `최종 작성본`을 저장할 때도 버전을 생성할 수 있다.
   - 실제 제출용 자기소개서의 변경 이력까지 추적할 수 있지만, AI 첨삭 이력과 사용자 편집 이력이 섞인다.

### 선택 이유

PRD의 버전 생성 트리거는 `AI첨삭 다시받기`에 직접 연결되어 있다. 따라서 버전의 의미를 AI 첨삭 결과로 제한하면 화면의 버전 히스토리와 API 리소스의 의미가 명확해진다.

### 트레이드오프

- 장점
  - 버전 히스토리가 AI 첨삭 이력이라는 하나의 의미를 가진다.
  - 재첨삭 결과 비교, 최신 첨삭 표시, 스트리밍 완료 후 버전 생성 흐름이 단순하다.
  - 사용자 편집 저장과 AI 첨삭 버전 생성 API를 분리할 수 있다.

- 단점
  - 사용자가 최종 작성본을 여러 번 저장한 이력은 버전 히스토리에 남지 않는다.
  - 최종 작성본 변경 이력을 추적하려면 별도의 감사 로그나 저장 이력 기능이 필요하다.



## Decision 004: AI 첨삭 결과는 질문별로 독립 저장한다

### 결정

AI 첨삭 결과는 자기소개서 전체에 대한 하나의 큰 리포트가 아니라, 자기소개서 질문별 결과로 저장한다.

각 첨삭 버전은 여러 개의 질문별 첨삭 결과를 가진다.

리소스 구조:

```text
ReviewVersion
ReviewVersionQuestionResult
```

`ReviewVersionQuestionResult`는 문항별로 다음 정보를 가진다.

```text
questionId
question
originalAnswer
maxAnswerLength
aiReport
rewrittenAnswer
finalAnswer
```

API 형태:

```http
GET /cover-letters/{coverLetterId}/review-versions/{versionId}

PUT /cover-letters/{coverLetterId}/review-versions/{versionId}/final-answers
```

### PRD 근거

- AI 첨삭 화면에는 `자기소개서 질문 + 내가 작성한 자기소개서 + AI 리포트 + Diff + 최종 작성본`이 각 질문마다 존재한다.
- `내가 작성한 자기소개서`와 `최종 작성본`에는 실시간 글자 수가 표시된다.
- 등록 step3에서 질문마다 최대 글자 수와 답변을 입력한다.

### 고려한 대안

1. 질문별 첨삭 결과 저장
   - 문항마다 AI 리포트, AI 수정본, 최종 작성본을 저장한다.
   - 화면 구조와 API 응답 구조가 일치한다.
   - 문항별 글자 수 제한과 최종 작성본 저장을 명확하게 처리할 수 있다.

2. 전체 자기소개서 첨삭 결과 저장
   - 자기소개서 전체에 대한 하나의 AI 리포트를 저장한다.
   - 저장 구조는 단순하지만, 문항별 최종 작성본 관리와 화면용 diff 계산 기준 제공이 어려워진다.

### 선택 이유

PRD의 첨삭 상세 화면은 문항별 결과를 전제로 한다. 각 문항은 질문, 최대 글자 수, 원본 답변, AI 리포트, AI 수정본, 최종 작성본을 독립적으로 보여줘야 한다. Diff는 원본 답변과 AI 수정본을 이용해 프론트엔드에서 계산한다.

### 트레이드오프

- 장점
  - 화면 요구사항과 데이터 모델이 직접 대응된다.
  - 문항별 글자 수와 최종 작성본 저장을 단순하게 처리할 수 있다.
  - 향후 문항별 재첨삭, 문항별 실패 상태, 문항별 품질 점수 같은 확장이 쉽다.

- 단점
  - 첨삭 버전 하위에 질문별 결과 리소스가 생겨 응답 구조가 깊어진다.
  - LLM이 전체 맥락을 보고 생성한 결과라도 저장 시 문항별로 분해해야 한다.



## Decision 006: 최종 작성본은 전체 문항을 일괄 저장한다

### 결정

AI 첨삭 화면의 `최종 작성본`은 문항별 개별 저장이 아니라, 화면 하단의 `저장하기` 버튼을 통해 전체 문항을 한 번에 저장한다.

API 형태:

```http
PUT /cover-letters/{coverLetterId}/review-versions/{versionId}/final-answers
```

요청은 첨삭 버전에 포함된 질문별 결과 ID와 최종 작성본을 배열로 전달한다.

```json
{
  "answers": [
    {
      "questionResultId": "rvqr_01HZ...",
      "finalAnswer": "저는 백엔드 개발자로서..."
    }
  ]
}
```

### PRD 근거

- AI 첨삭 화면에서 `최종 작성본` 입력란은 각 질문마다 존재한다.
- 화면 하단에는 하나의 `저장하기` 버튼이 있다.
- 사용자는 AI 리포트를 참고하여 최종 작성본을 직접 작성한 뒤 저장한다.

### 고려한 대안

1. 전체 문항 일괄 저장
   - 하단 `저장하기` 버튼을 누르면 해당 첨삭 버전의 모든 문항 최종 작성본을 한 번에 저장한다.
   - 사용자가 “이번 첨삭 결과에 대한 최종본 전체를 저장했다”고 이해하기 쉽다.

2. 문항별 저장
   - 각 문항의 최종 작성본을 개별 API로 저장한다.
   - 자동 저장이나 부분 저장에는 유리하지만, PRD의 단일 `저장하기` 버튼과는 의미가 덜 직접적이다.

### 선택 이유

PRD는 첨삭 화면 하단에 하나의 `저장하기` 버튼을 둔다. 따라서 저장 행위의 단위를 특정 문항이 아니라 현재 첨삭 버전의 전체 최종 작성본으로 해석하는 것이 화면 흐름과 가장 잘 맞는다.

### 트레이드오프

- 장점
  - 화면 UX와 API 의미가 일치한다.
  - 저장 성공 여부를 전체 최종본 기준으로 명확히 표현할 수 있다.
  - 사용자가 저장하지 않은 문항이 있는지 검증하기 쉽다.

- 단점
  - 한 문항만 수정해도 전체 문항의 최종 작성본 payload를 보내야 한다.
  - 자동 저장을 도입하려면 별도 API를 추가하거나 같은 API를 더 자주 호출해야 한다.



## Decision 012: 재첨삭 요구사항은 최대 1000자로 제한한다

### 결정

`AI첨삭 다시받기` 모달의 재첨삭 요구사항 필드인 `requestInstruction`은 최대 1000자로 제한한다.

예상 validation:

```text
requestInstruction: 선택, 최대 1000자
```

### PRD 근거

- `AI첨삭 다시받기` 버튼을 누르면 모달창이 뜬다.
- 모달창에서 첨삭 요구사항을 작성하고, 모달창의 `AI 첨삭 다시받기` 버튼을 누르면 AI 첨삭이 시작된다.

### 고려한 대안

1. 500자
   - 짧고 명확한 첨삭 요구사항만 받게 된다.
   - 여러 문항에 대한 세부 요청을 쓰기에는 부족할 수 있다.

2. 1000자
   - 사용자가 첨삭 방향을 충분히 구체적으로 쓸 수 있다.
   - UI와 validation 부담이 크지 않고, LLM 프롬프트 길이도 관리 가능한 수준이다.

3. 3000자
   - 채용 우대사항과 비슷한 수준의 상세한 지시를 받을 수 있다.
   - 재첨삭 프롬프트가 길어져 비용과 품질 관리가 어려워질 수 있다.

### 선택 이유

재첨삭 요구사항은 자기소개서 본문이나 채용 우대사항이 아니라 첨삭 방향을 보완하는 입력이다. 500자는 다소 짧고 3000자는 과하므로, 1000자가 사용자 표현력과 LLM 입력 관리 사이의 균형이 좋다.

### 트레이드오프

- 장점
  - 사용자가 구체적인 재첨삭 방향을 작성할 수 있다.
  - LLM 프롬프트 길이를 과도하게 늘리지 않는다.
  - 프론트엔드 모달 UI에서도 글자 수 안내와 validation이 단순하다.

- 단점
  - 문항별로 매우 상세한 지시를 쓰고 싶은 사용자는 제한을 느낄 수 있다.
  - 향후 문항별 재첨삭 요구사항을 지원하려면 별도 입력 구조가 필요할 수 있다.



## Decision 013: AI 리포트는 단일 문자열로 제공한다

### 결정

AI 첨삭 화면의 `aiReport`는 STAR, 구체성, 우대사항 적합성 같은 평가 항목별 객체가 아니라 프론트엔드에 그대로 렌더링할 단일 문자열로 제공한다.

평가 기준은 API 응답 필드로 고정하지 않고, LLM 프롬프트와 서버 내부 생성 정책에 명시한다.

예상 구조:

```json
{
  "aiReport": "STAR 관점에서 상황과 과제는 드러나지만 행동과 결과가 약합니다. 성과 수치와 직무 키워드를 보강하면 더 설득력 있습니다."
}
```

### PRD 근거

- AI 첨삭 화면에는 `AI 리포트` 영역이 있고, 해당 영역은 LLM 응답을 스트리밍 형식으로 보여준다.
- PRD는 첨삭 기준을 나열하지만, 화면에서 기준별로 별도 필드를 렌더링한다고 명시하지 않는다.

### 고려한 대안

1. 고정 필드 구조
   - `starEvaluation`, `specificityEvaluation`, `preferenceFitEvaluation`처럼 평가 항목별 필드를 제공한다.
   - 화면 렌더링과 데이터 분석은 안정적이지만, LLM 출력과 파싱 계약이 빡빡해진다.

2. 단일 문자열 구조
   - 프론트엔드는 `aiReport` 문자열 하나를 렌더링한다.
   - 평가 기준은 프롬프트에 명시하고, LLM은 이를 반영한 자연어 리포트를 생성한다.

### 선택 이유

프론트엔드에서는 AI 리포트를 하나의 문자열로 보여줄 계획이다. 따라서 API 응답을 평가 항목별 필드로 고정하면 현재 화면 요구보다 과한 계약이 된다. 평가 기준은 LLM 프롬프트에 명확히 포함하고, API는 렌더링에 필요한 문자열을 안정적으로 전달하는 쪽이 더 단순하다.

### 트레이드오프

- 장점
  - API 응답 구조가 단순하다.
  - LLM 리포트 표현이 유연하다.
  - 평가 기준을 추가하거나 문장 구성을 바꿔도 API 계약 변경이 적다.

- 단점
  - 평가 항목별 데이터 분석이나 필터링이 어렵다.
  - 특정 평가 항목이 누락되었는지 API 레벨에서 검증하기 어렵다.
  - 향후 항목별 UI를 만들려면 구조화 필드를 추가해야 한다.



## Decision 014: Diff는 프론트엔드에서 계산한다

### 결정

AI 첨삭 화면의 Diff는 서버가 생성하거나 저장하지 않는다.

API는 문항별 `originalAnswer`와 `rewrittenAnswer`를 제공하고, 프론트엔드는 두 문자열을 비교해 git diff와 유사한 초록/빨강 변경 표시를 계산한다.

응답 구조:

```json
{
  "originalAnswer": "제가 지원한 이유는...",
  "rewrittenAnswer": "저는 백엔드 개발자로서..."
}
```

### PRD 근거

- Diff 부분에서는 사용자가 쓴 자기소개서와 AI 리포트를 비교하여 변동 부분을 색으로 처리해 보여준다.
- PRD의 Diff는 저장 이력이라기보다 화면 표시 요구에 가깝다.

### 고려한 대안

1. 서버가 diff를 생성해서 저장
   - API가 `diff: [{ type, text }]` 형태로 내려준다.
   - 모든 클라이언트에서 동일한 diff 결과를 보장할 수 있지만, 서버가 diff 알고리즘과 저장 구조를 책임져야 한다.

2. 프론트엔드가 원문과 AI 수정본으로 diff 계산
   - API는 `originalAnswer`, `rewrittenAnswer`만 내려준다.
   - 프론트엔드가 화면 렌더링 시 diff를 계산한다.

### 선택 이유

Diff는 현재 PRD에서 화면 표시용 기능이다. 이미 API가 원문과 AI 수정본을 모두 제공하므로, 서버가 별도 diff 결과를 저장하는 것은 현재 요구보다 과하다.

### 트레이드오프

- 장점
  - 서버 저장 모델과 API 응답이 단순해진다.
  - diff 렌더링 정책을 프론트엔드에서 빠르게 조정할 수 있다.
  - 원문과 수정본만 있으면 언제든 diff를 재계산할 수 있다.

- 단점
  - diff 결과가 프론트엔드 구현에 종속된다.
  - 여러 클라이언트가 생기면 diff 표시가 달라질 수 있다.
  - 서버에 diff 이력이 남지 않는다.



## Decision 015: 첨삭 버전 라벨은 v0.1부터 순차 증가한다

### 결정

AI 첨삭 버전 라벨은 최초 첨삭 결과를 `v0.1`로 표시하고, 재첨삭이 완료될 때마다 `v0.2`, `v0.3`처럼 patch 숫자를 1씩 증가시킨다.

이 라벨은 semantic versioning이 아니라 화면 표시용 revision label이다. `major`, `minor`, `patch`에 제품 호환성 의미를 부여하지 않는다.

예상 흐름:

```text
최초 첨삭 완료: v0.1
1번째 재첨삭 완료: v0.2
2번째 재첨삭 완료: v0.3
```

### PRD 근거

- 버전 히스토리에는 `v0.1` 같은 버전 표시와 기록 시각이 나타난다.
- 새로 첨삭된 자기소개서는 새로운 버전으로 생성되어 저장된다.
- 최근 버전이 무엇인지 표시되어 있다.

### 고려한 대안

1. `v0.1`, `v0.2`, `v0.3` 순차 증가
   - PRD 예시와 일치한다.
   - 사용자에게 버전 히스토리 형태로 익숙하게 보인다.

2. `r1`, `r2`, `r3` 또는 `versionNumber: 1`
   - 첨삭 회차라는 의미가 더 직접적이다.
   - 하지만 PRD의 `v0.1` 예시와 다르다.

### 선택 이유

PRD가 이미 `v0.1` 형태의 버전 표시를 예시로 제시한다. 따라서 화면 표시 라벨은 PRD와 맞추되, semantic versioning으로 오해하지 않도록 revision label임을 명시한다.

### 트레이드오프

- 장점
  - PRD 예시와 일치한다.
  - 버전 히스토리에서 사용자가 쉽게 최신/이전 버전을 구분할 수 있다.
  - 구현은 첨삭 완료 횟수를 기준으로 단순하게 처리할 수 있다.

- 단점
  - semantic versioning처럼 보일 수 있다.
  - `v1.0` 같은 큰 버전 전환 의미는 현재 정의하지 않는다.



## Decision 036: ReviewVersion은 성공한 첨삭 결과만 생성한다

### 결정

`ReviewVersion`은 LLM 첨삭 또는 재첨삭 Job이 성공적으로 완료된 경우에만 생성한다.

진행 중이거나 실패한 첨삭 시도는 `ReviewVersion`으로 저장하지 않는다. 해당 상태는 `LlmJob`과 `CoverLetter.status`로 표현한다.

상태 표현:

```text
최초 첨삭 진행: CoverLetter.status=REVIEWING, LlmJob.status=PENDING|PROCESSING
최초 첨삭 성공: CoverLetter.status=REVIEWED, ReviewVersion(v0.1) 생성
최초 첨삭 실패: CoverLetter.status=REVIEW_FAILED, LlmJob.status=FAILED

재첨삭 진행: CoverLetter.status=REVIEWED 유지, LlmJob.status=PENDING|PROCESSING
재첨삭 성공: CoverLetter.status=REVIEWED 유지, 새 ReviewVersion(v0.n) 생성
재첨삭 실패: CoverLetter.status=REVIEWED 유지, LlmJob.status=FAILED
```

`ReviewVersion`은 성공한 첨삭 결과만 저장하므로 별도의 `status` 필드를 갖지 않는다. 진행 중, 실패, 취소 상태는 `LlmJob.status`로만 표현한다.

### PRD 근거

- PRD는 새로 첨삭된 자기소개서가 새로운 버전으로 생성되어 저장된다고 설명한다.
- 버전 히스토리에는 `v0.1` 같은 버전 표시와 기록 시각, 최근 버전 여부가 나타난다.
- 사용자가 버전 히스토리에서 기대하는 것은 열람 가능한 첨삭 결과물이다.

### 고려한 대안

1. 성공한 첨삭 결과만 `ReviewVersion` 생성
   - 버전 히스토리에는 실제 첨삭 결과가 있는 버전만 남는다.
   - 실패 이력은 `LlmJob`에서 확인한다.

2. Job 시작 시 `ReviewVersion` 생성
   - `PROCESSING`, `FAILED` 버전도 히스토리에 남길 수 있다.
   - 하지만 결과 없는 버전이 생기고, 사용자가 열람할 수 없는 버전을 화면에서 다뤄야 한다.

3. 진행 중에는 임시 `ReviewVersion` 생성 후 실패 시 삭제
   - 성공 시 전환은 쉽지만, 실패/삭제 타이밍과 새로고침 복구 정책이 복잡해진다.

### 선택 이유

버전은 사용자가 나중에 다시 열람하고 비교할 수 있는 첨삭 결과물이어야 한다. 실패한 LLM 시도는 결과물이 아니라 작업 이력이므로 `LlmJob`이 담당하는 것이 역할 분리가 명확하다.

### 트레이드오프

- 장점
  - 버전 히스토리에 결과 없는 항목이 나타나지 않는다.
  - `ReviewVersionQuestionResult`가 없는 버전을 처리하지 않아도 된다.
  - 기존 성공 버전이 재첨삭 실패로 오염되지 않는다.

- 단점
  - 사용자가 실패한 재첨삭 시도를 버전 히스토리에서 직접 확인할 수 없다.
  - 실패 원인 확인은 `LlmJob` 상태 조회나 별도 알림/토스트에 의존한다.



## Decision 037: 최종 작성본은 최신 ReviewVersion에서만 수정할 수 있다

### 결정

`최종 작성본` 저장 API는 최신 `ReviewVersion`에 대해서만 허용한다.

과거 `ReviewVersion`은 버전 히스토리 열람과 비교 용도로만 사용하고, 최종 작성본을 수정할 수 없다.

적용 API:

```http
PUT /cover-letters/{coverLetterId}/review-versions/{versionId}/final-answers
```

Validation:

```text
versionId는 해당 자기소개서의 최신 ReviewVersion이어야 한다.
```

최신 버전이 아닌 경우:

```text
CONFLICT
REVIEW_VERSION_NOT_LATEST
```

최신 버전의 최종 작성본을 저장해도 새 `ReviewVersion`은 생성하지 않는다.

### PRD 근거

- PRD에서 `저장하기` 버튼은 현재 AI 첨삭 화면 하단에 존재한다.
- `저장하기`를 누르면 기존과 동일한 버전으로 일괄 저장된다고 설명한다.
- 버전 히스토리는 AI 첨삭 결과 기록을 보여주는 용도다.

### 고려한 대안

1. 최신 `ReviewVersion`만 최종 작성본 수정 가능
   - 과거 버전은 히스토리로 보고 읽기 전용으로 유지한다.
   - 현재 작업 대상과 과거 기록의 역할이 분리된다.

2. 모든 `ReviewVersion`의 최종 작성본 수정 가능
   - 과거 첨삭본도 다시 다듬을 수 있다.
   - 하지만 히스토리로 남은 과거 버전의 내용이 계속 바뀔 수 있다.

3. 과거 버전 수정 시 새 버전 생성
   - 이력은 보존된다.
   - 하지만 `AI첨삭 다시받기`만 새 버전을 만든다는 기존 결정과 충돌한다.

### 선택 이유

버전 히스토리는 과거 AI 첨삭 결과를 안정적으로 열람하고 비교하기 위한 기록이다. 과거 버전의 최종 작성본까지 수정 가능하게 만들면 히스토리의 의미가 흐려지고, 현재 제출용 최종본이 어느 버전을 기준으로 관리되는지도 애매해진다. 따라서 최신 버전만 수정 가능하게 제한한다.

### 트레이드오프

- 장점
  - 과거 버전이 읽기 전용 기록으로 안정적으로 유지된다.
  - 최종 작성본의 현재 작업 대상이 명확하다.
  - 사용자가 직접 저장하는 행위로 새 버전이 생성되지 않는 기존 정책과 일관된다.

- 단점
  - 사용자가 과거 첨삭 버전을 기준으로 다시 작성하고 싶다면, 최신 버전으로 재첨삭하거나 별도 복원 기능이 필요하다.
  - 과거 버전별 최종 작성본을 개별적으로 다듬는 워크플로는 지원하지 않는다.



## Decision 038: 최종 작성본 저장 payload는 전체 문항을 항상 포함한다

### 결정

최종 작성본 저장 API는 변경된 문항만 보내는 부분 저장을 지원하지 않는다.

클라이언트는 최신 `ReviewVersion`에 포함된 모든 `ReviewVersionQuestionResult`의 `questionResultId`와 `finalAnswer`를 `answers` 배열에 포함해야 한다.

적용 API:

```http
PUT /cover-letters/{coverLetterId}/review-versions/{versionId}/final-answers
```

Validation:

```text
answers는 첨삭 버전에 포함된 모든 questionResultId를 포함해야 한다.
누락된 questionResultId가 있으면 VALIDATION_ERROR를 반환한다.
존재하지 않는 questionResultId가 있으면 VALIDATION_ERROR를 반환한다.
중복된 questionResultId가 있으면 VALIDATION_ERROR를 반환한다.
```

### PRD 근거

- PRD의 AI 첨삭 화면에는 문항별 `최종 작성본` 입력란이 있고, 화면 하단에는 하나의 `저장하기` 버튼이 있다.
- `저장하기`를 누르면 기존과 동일한 버전으로 일괄 저장된다고 설명한다.
- 이미 Decision 006에서 최종 작성본은 전체 문항을 일괄 저장하기로 결정했다.

### 고려한 대안

1. 전체 문항을 항상 모두 보내야 함
   - 저장 payload가 현재 첨삭 버전의 전체 최종 작성본을 대표한다.
   - 누락 문항 검증이 명확하다.

2. 변경된 문항만 부분 저장 가능
   - payload는 작아진다.
   - 하지만 부분 업데이트, 동시 수정, 누락 처리, 저장 완료 기준이 복잡해진다.

3. 전체 저장과 부분 저장을 모두 지원
   - 프론트엔드 선택지는 늘어난다.
   - 하지만 API 표면이 커지고 동일 기능의 저장 경로가 둘로 나뉜다.

### 선택 이유

현재 화면에는 하나의 저장 버튼이 있고, 사용자는 해당 첨삭 버전의 최종 작성본 전체를 저장한다고 이해하는 것이 자연스럽다. 부분 저장을 지원하지 않으면 저장 성공 여부와 서버 상태를 전체 문항 기준으로 단순하게 검증할 수 있다.

### 트레이드오프

- 장점
  - 저장 결과가 항상 전체 최종 작성본 기준으로 완결된다.
  - 누락, 중복, 잘못된 문항 ID를 검증하기 쉽다.
  - Decision 006의 전체 문항 일괄 저장 정책과 일관된다.

- 단점
  - 한 문항만 수정해도 전체 문항 payload를 다시 보내야 한다.
  - 문항 수가 많아질수록 요청 크기가 커질 수 있다.
  - 향후 자동 저장을 도입하면 별도 부분 저장 API를 다시 설계해야 할 수 있다.



## Decision 039: 최종 작성본은 빈 문자열로 저장할 수 없다

### 결정

최종 작성본 `finalAnswer`는 필수이며, 빈 문자열을 허용하지 않는다.

제약:

```text
finalAnswer: 1~5000자
```

적용 API:

```http
PUT /cover-letters/{coverLetterId}/review-versions/{versionId}/final-answers
```

`finalAnswer`가 빈 문자열이면 `VALIDATION_ERROR`를 반환한다.

### PRD 근거

- AI 첨삭 화면의 `최종 작성본`은 사용자가 AI 리포트를 참고해 실제 제출 후보 문장을 작성하는 영역이다.
- PRD는 화면에서 글자 수를 보여주며, 저장하기 버튼으로 최종 작성본을 저장한다고 설명한다.
- 자기소개서 답변은 내용이 있는 문장이어야 한다.

### 고려한 대안

1. 빈 문자열 불가, 1~5000자
   - 저장 완료된 최종 작성본이 비어 있는 상태를 막을 수 있다.
   - 제출 후보 문장이라는 의미와 맞다.

2. 빈 문자열 허용, 0~5000자
   - 사용자가 임시로 내용을 지워둘 수 있다.
   - 하지만 저장 완료 상태인데 답변이 비어 있는 애매한 상태가 생긴다.

### 선택 이유

최종 작성본은 단순 메모나 임시 입력값이 아니라 제출 후보 자기소개서 문장이다. 빈 문자열 저장을 허용하면 “저장 완료”와 “작성되지 않음” 상태가 섞인다. 따라서 최소 1자 이상을 요구한다.

### 트레이드오프

- 장점
  - 저장된 최종 작성본이 항상 내용 있는 답변임을 보장한다.
  - 결과 화면과 제출용 복사 흐름에서 빈 답변을 방지할 수 있다.
  - 원본 답변의 `1~5000자` 제약과 일관된다.

- 단점
  - 사용자가 특정 문항을 비워둔 채 전체 저장할 수 없다.
  - 내용을 모두 지우고 나중에 다시 작성하는 임시 워크플로는 지원하지 않는다.



## Decision 040: 최종 작성본은 앞뒤 공백을 trim한 뒤 검증하고 저장한다

### 결정

최종 작성본 `finalAnswer`는 서버에서 앞뒤 공백을 제거한 뒤 길이를 검증한다.

서버는 trim된 값을 저장한다.

적용 API:

```http
PUT /cover-letters/{coverLetterId}/review-versions/{versionId}/final-answers
```

검증 순서:

```text
1. finalAnswer 앞뒤 공백 제거
2. trim된 finalAnswer가 1~5000자인지 검증
3. trim된 finalAnswer 저장
```

예시:

```text
"  저는 백엔드 개발자로서...  " -> "저는 백엔드 개발자로서..."
"   " -> VALIDATION_ERROR
```

### PRD 근거

- 최종 작성본은 실제 제출 후보 문장이다.
- PRD는 최종 작성본의 글자 수를 화면에서 보여주고 저장한다고 설명한다.
- 앞뒤 공백은 자기소개서 답변의 의미 있는 본문으로 보기 어렵다.

### 고려한 대안

1. 앞뒤 공백 trim 후 길이 검증 및 저장
   - 공백만 있는 입력을 빈 값으로 처리할 수 있다.
   - 실수로 입력된 앞뒤 공백을 정리해 저장할 수 있다.

2. 원문 그대로 저장
   - 사용자가 입력한 문자열을 완전히 보존한다.
   - 하지만 공백만 있는 답변이 1자 이상 검증을 통과할 수 있다.

### 선택 이유

Decision 039에서 최종 작성본은 빈 문자열로 저장할 수 없다고 결정했다. 앞뒤 공백을 제거하지 않으면 `"   "` 같은 값이 내용 없는 답변인데도 길이 검증을 통과할 수 있다. 따라서 trim 후 검증하고, 저장값도 trim된 값으로 통일한다.

### 트레이드오프

- 장점
  - 공백만 있는 최종 작성본 저장을 방지할 수 있다.
  - 저장된 답변의 데이터 품질이 좋아진다.
  - 프론트엔드와 백엔드의 빈 값 판단 기준을 단순화할 수 있다.

- 단점
  - 사용자가 의도적으로 앞뒤 공백을 넣어도 보존되지 않는다.
  - 원문 입력을 완전 그대로 보관하는 요구가 생기면 별도 raw value 저장 정책이 필요하다.
